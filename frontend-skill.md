# Website Design Skill

A production-oriented skill for designing and building **any type of
modern website or web application**. The default visual direction is
**minimal, clean, calm, highly legible, responsive, accessible, and
professional**, but the skill adapts to the user's brief rather than
forcing a fixed aesthetic.

The skill is intentionally broad: a one-page landing page, a multi-page
corporate site, a SaaS product, an authenticated dashboard, an
e-commerce storefront, a portfolio, a media site, a documentation
portal, an educational platform, a marketplace, a community product, a
booking flow, or a complex web application should all use the same
underlying process while changing information architecture, interaction
density, and component strategy.

> **Operating principle:** design the experience, not just the pixels.
> Every element must have a purpose, communicate hierarchy, behave
> predictably, and survive real content, real devices, keyboard
> navigation, zoom, slow networks, and error states.

## Agent operating contract

When this skill is used by an AI model or coding agent, treat the
following order as the priority hierarchy:

``` text
1. User intent and explicit constraints
2. Safety, accessibility, and platform/standards requirements
3. Content truthfulness and real-data integrity
4. Information architecture and task clarity
5. Responsive structure and semantic HTML
6. Design-system consistency
7. Typography, spacing, imagery, and component craft
8. Interaction and motion polish
9. Decorative expression
```

When two visual ideas conflict, prefer the one higher in this hierarchy.

### Never optimize for visual novelty at the expense of usability

The agent must not add a visual treatment merely because:

-   there is empty space
-   a generated design "looks too simple"
-   a reference uses it
-   a template contains it
-   it demonstrates technical capability
-   it makes a screenshot look more impressive

The agent should first ask whether the treatment improves a user task,
hierarchy, brand identity, comprehension, feedback, or useful
atmosphere.

### Never invent production facts

Do not fabricate:

-   reviews
-   customer counts
-   awards
-   locations
-   opening hours
-   prices
-   product availability
-   testimonials
-   partners
-   certifications
-   performance claims
-   business addresses
-   social links
-   metrics
-   statistics

When information is missing, use clearly marked placeholders or neutral
copy rather than making realistic-looking facts.

### Treat assumptions as visible implementation decisions

For missing information, record material assumptions such as:

``` text
ASSUMPTION:
The client has not provided a real address, so the location is represented generically.

ASSUMPTION:
Checkout is not connected, so the cart interaction is demonstrative only.
```

Do not quietly turn assumptions into "facts."

### Prefer the simplest architecture that meets the brief

Do not introduce:

-   unnecessary frameworks
-   unnecessary dependencies
-   unnecessary animation libraries
-   unnecessary component abstractions
-   unnecessary state management
-   unnecessary build tooling

A technically sophisticated implementation is not automatically a better
implementation.

## 1. Core operating rules

### 1.1 Start from intent

Before designing, determine:

-   who the site is for
-   what the user is trying to accomplish
-   what the business/product needs to accomplish
-   the primary conversion or success event
-   the trust signals needed to support that event
-   what information must be visible immediately
-   what can be progressive disclosure
-   what content is authoritative vs illustrative
-   what must work without JavaScript
-   which constraints are explicit and which are assumptions

### 1.2 Minimal does not mean empty

Use minimalism as **reduction of friction**, not decoration removal.

A useful test is:

> If removing an element makes the user's task harder, the interface was
> not actually simplified.

Apple's current design guidance explicitly distinguishes simplicity from
minimalism: simplicity is about removing friction, strengthening clarity
and hierarchy, and including enough context for people to act
confidently. [Apple, WWDC26 --- Principles of great
design](https://developer.apple.com/videos/play/wwdc2026/250/)

### 1.3 Prefer systems over isolated styling

Create reusable decisions for:

-   spacing
-   type scale
-   color roles
-   radii
-   borders
-   elevation
-   icons
-   controls
-   layout containers
-   breakpoints
-   motion
-   component states
-   accessibility

This makes the page feel intentional instead of assembled from unrelated
pieces. Atlassian's current design-system guidance similarly treats
tokens, spacing, grid, typography, color, elevation, borders, and radius
as foundations for consistent interfaces. [Atlassian
Design](https://atlassian.design/foundations)

### 1.4 Design every state

Never design only the ideal state. Include, where relevant:

`default → hover → focus → active → disabled → loading → success → empty → partial → error → offline → permission-limited`

Vercel's Web Interface Guidelines explicitly calls for all
states---including empty, sparse, dense, and error states---and for
keyboard-operable flows with visible focus. [Vercel Web Interface
Guidelines](https://vercel.com/design/guidelines)

### 1.5 Make the interface adapt to the content

Avoid brittle positioning. Prefer semantic HTML, normal document flow,
CSS Grid/Flexbox, intrinsic sizing, container queries when useful, and
fluid type/spacing where appropriate.

MDN describes responsive design as an approach that lets layouts adapt
across device sizes using flexible grids, fluid media, media queries,
and modern CSS layout tools. [MDN --- Responsive
design](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/CSS_layout/Responsive_Design)

# 2. The mandatory workflow

Use this sequence for substantial website work:

## THINK → RESEARCH → PLAN → START → PRESENT

### Phase A --- THINK

Turn the user's request into a design problem.

Output internally:

``` text
Goal:
Audience:
Primary user task:
Primary business outcome:
Secondary outcomes:
Content priorities:
Conversion/event:
Tone:
Visual direction:
Functional requirements:
Technical constraints:
Known assets:
Unknowns:
Assumptions:
Success criteria:
```

Do not prematurely choose a visual style before understanding the
problem.

### Phase B --- RESEARCH

Research only what materially improves the result.

Inspect:

-   user-provided references
-   current product/site
-   competitors or category norms
-   official platform/design systems
-   accessibility requirements
-   browser/frontend constraints
-   relevant interaction patterns
-   current web performance guidance
-   current typography or asset requirements

Use **primary sources first** for technical/design-system claims.

Research outputs should be distilled into:

``` text
Keep:
Avoid:
Adapt:
Prove:
```

Do not copy a reference website. Extract transferable principles such as
hierarchy, pacing, information density, navigation, image scale, motion
timing, or component treatment.

### Phase C --- PLAN

Produce enough structure that implementation becomes predictable.

Define:

1.  sitemap / page map
2.  page goals
3.  user flows
4.  content hierarchy
5.  design tokens
6.  layout grid
7.  component inventory
8.  responsive behavior
9.  interaction/state matrix
10. accessibility model
11. motion model
12. data/model requirements when the site is app-like
13. validation plan

### Phase D --- START

Build from the system outward:

``` text
Foundation → Layout → Navigation → Hero/Primary task → Content sections → Components → States → Responsive behavior → Motion → Polish → QA
```

Prefer semantic, reusable components. Avoid duplicated one-off CSS when
the pattern appears more than once.

### Phase E --- PRESENT

Present the result in the format implied by the request.

A good delivery contains:

-   what was built/designed
-   important design decisions
-   how the structure maps to the user's goals
-   notable responsive behavior
-   notable accessibility/performance choices
-   how to run/use the deliverable, when code is provided
-   any material assumptions

Do not bury the usable output under a long design essay.

  X"             implementation with similar functional qualities, never

## 3.2 Do not lock the user into a template

Adapt:

-   page count
-   density
-   navigation complexity
-   CTA quantity
-   color strategy
-   imagery
-   motion
-   content length
-   component complexity
-   authentication model
-   data visualization
-   commerce mechanics
-   accessibility treatment
-   technical stack

to the actual brief.

There is no arbitrary maximum page count, component count, section
count, animation count, or code size. Scale with the project. Avoid
complexity merely to demonstrate capability.

# 4. Website-type playbooks

## 4.1 Marketing / landing page

Typical hierarchy:

`Announcement → Navigation → Hero → Proof → Core value → Features → Product/demo → Social proof → Pricing/CTA → FAQ → Footer`

Use fewer sections when the product is simple. Use more when progressive
explanation is necessary.

Hero checklist:

-   clear one-line value proposition
-   supporting explanation
-   primary CTA
-   optional secondary action
-   immediate proof or product context
-   obvious visual focal point
-   mobile version designed independently, not merely scaled down

## 4.2 SaaS product site

Optimize for:

-   category understanding
-   product comprehension
-   feature discovery
-   proof
-   use cases
-   pricing
-   security/trust
-   activation path

Use interactive product visuals when they communicate behavior better
than static marketing art.

## 4.3 Web application / authenticated product

Prioritize:

-   information architecture
-   task completion
-   density control
-   persistent navigation
-   search/filter/sort
-   tables and forms
-   keyboard behavior
-   permissions
-   empty/loading/error states
-   undo/recovery
-   responsive adaptation

Avoid making a dashboard look like a marketing page. Functional density
is part of the design.

## 4.4 E-commerce

Primary flow:

`Discovery → Category/Collection → Product → Options → Cart → Checkout → Confirmation`

Design for:

-   product imagery
-   variant clarity
-   availability
-   price/discount transparency
-   delivery context
-   reviews/proof
-   related products
-   sticky mobile actions when appropriate
-   error recovery in cart/checkout

Shopify recommends intuitive product discovery, prominent navigation,
clear entry points into collections, responsive layouts, and accessible
interactions. [Shopify Theme
Design](https://shopify.dev/docs/storefronts/themes/best-practices/design)

## 4.5 Portfolio / agency / studio

Optimize for:

-   instant creative positioning
-   work discovery
-   case-study depth
-   visual pacing
-   client proof
-   contact/conversion

Use editorial rhythm rather than filling every viewport with UI.

## 4.6 Documentation / developer portal

Optimize for:

-   search
-   persistent table of contents
-   copyable code
-   clear headings
-   versioning
-   API navigation
-   feedback
-   keyboard access
-   deep-linkable sections

## 4.7 Blog / editorial / media

Optimize for:

-   typographic readability
-   content discovery
-   metadata
-   related stories
-   search
-   author context
-   sharing
-   image performance
-   semantic structure

## 4.8 Education / course platform

Optimize for:

-   course progression
-   lesson hierarchy
-   progress state
-   accessible media
-   assessments
-   notes/bookmarks
-   resume flow

## 4.9 Marketplace / directory

Optimize for:

-   search
-   filters
-   ranking context
-   comparison
-   trust signals
-   profile detail
-   map/list views where useful
-   saved items

## 4.10 Community / social product

Optimize for:

-   content creation
-   feeds
-   replies/reactions
-   notifications
-   moderation/reporting
-   profile identity
-   privacy controls
-   clear relationship states

## 4.11 Booking / service website

Optimize for:

`service → availability → selection → details → confirmation`

Keep schedules, price, timezone, cancellation rules, and errors obvious.

## 4.12 Restaurant / hospitality / local business

Prioritize:

-   location
-   hours
-   menu/services
-   booking/contact
-   imagery
-   reviews/proof
-   accessibility information
-   mobile-first actions

# 5. Information architecture

Start with user questions, not with components.

For every page, answer:

1.  What is this?
2.  Why should I care?
3.  What can I do here?
4.  What do I need to decide?
5.  What happens next?

A strong page has an explicit **visual hierarchy**:

``` text
Level 1 — primary outcome
Level 2 — explanation/proof
Level 3 — supporting details
Level 4 — utility / secondary context
```

Keep navigation labels concise and predictable. Use familiar patterns
for familiar actions.

# 6. Visual system

## 6.1 Typography

Default starting point (adapt as needed):

-   one primary UI/type family
-   optional display family only when the brand benefits from it
-   clear distinction between display, heading, body, label, metadata,
    code
-   comfortable line length
-   optical rather than purely mathematical sizing
-   fluid typography for large displays when useful

Do not choose fonts based only on popularity. Check:

-   available weights
-   character support
-   x-height and readability
-   variable-font support
-   loading cost
-   licensing
-   numerals
-   italics
-   rendering quality across platforms

Google Design identifies Google Fonts as a central web-typography
resource, alongside Material Design. [Google
Design](https://design.google/about)

## 6.2 Spacing

Use a coherent spacing rhythm. A 4px or 8px-derived scale is a useful
starting point, not a law.

Example token set:

``` css
--space-1: 0.25rem;
--space-2: 0.5rem;
--space-3: 0.75rem;
--space-4: 1rem;
--space-5: 1.25rem;
--space-6: 1.5rem;
--space-8: 2rem;
--space-10: 2.5rem;
--space-12: 3rem;
--space-16: 4rem;
--space-20: 5rem;
```

Adjust the system when content or brand expression requires it.

## 6.3 Color

Define semantic roles rather than sprinkling raw hex values everywhere:

``` text
background
surface
surface-subtle
text-primary
text-secondary
text-tertiary
border
accent
accent-foreground
success
warning
error
focus
scrim
```

For minimal professional design, neutral surfaces and restrained accent
usage are usually easier to maintain than many saturated colors.

Never rely on color alone to communicate state.

## 6.4 Shape

Use one radius family with deliberate variation:

``` text
control radius < card radius ≤ panel radius
```

Avoid mixing random rounded shapes.

## 6.5 Borders and elevation

Use borders for structure and subtle shadows/elevation for hierarchy.
Vercel's guidelines recommend crisp borders, layered shadows, coherent
hue treatment, and nested radii. [Vercel Web Interface
Guidelines](https://vercel.com/design/guidelines)

## 6.6 Iconography

-   use a single icon family where possible
-   align icon optical size with text rather than box dimensions only
-   provide accessible names for meaningful icons
-   avoid decorative icon overload
-   do not use icons as a substitute for clear labels when the action
    could be ambiguous

# 7. Layout system

Use a layout system, not ad-hoc widths.

Recommended conceptual model:

``` text
viewport
  └─ full-bleed section
       └─ container
            └─ grid / flex layout
                 └─ content block
                      └─ component
```

A common container can be expressed as:

``` css
.container {
  width: min(100% - 2 * var(--gutter), var(--content-max));
  margin-inline: auto;
}
```

For marketing sites, use wider visual canvases while controlling reading
measure. For data-heavy products, optimize for task visibility rather
than decorative whitespace.

### Grid rules

Use Grid when the relationship between rows and columns matters. Use
Flexbox when the relationship is primarily one-dimensional. Let the
layout respond to available space rather than targeting a list of device
names.

# 8. Responsive design

Design the system for **continuous adaptation**.

Check at minimum:

-   narrow mobile
-   larger mobile
-   tablet / compact desktop
-   normal desktop
-   wide desktop
-   very wide viewport

Do not assume a single 768px or 1024px breakpoint solves responsiveness.

Check:

-   text wrapping
-   navigation collapse
-   card stacking
-   action priority
-   table behavior
-   image cropping
-   form layout
-   sticky elements
-   modal behavior
-   touch targets
-   zoom up to 400%
-   landscape orientation

The web.dev accessible-responsive-design guidance specifically
recommends flexible grids, preserving user zoom, and letting the
viewport/content determine layout behavior.
[web.dev](https://web.dev/articles/accessible-responsive-design)

# 9. Accessibility as a design requirement

Treat accessibility as part of the design system---not as a final audit.

Baseline requirements:

-   semantic HTML
-   logical heading hierarchy
-   visible keyboard focus
-   full keyboard operability
-   labeled form controls
-   usable error messages
-   accessible names for controls
-   alt text where meaningful
-   captions/transcripts where required
-   sufficient text/control contrast
-   reduced-motion alternative
-   no keyboard traps
-   predictable focus management
-   responsive text
-   zoom-friendly layout
-   color-independent status communication

Use WCAG 2.2 as the standards reference for broad web content
accessibility. [W3C WCAG 2.2](https://www.w3.org/TR/wcag/)

web.dev's accessibility guidance emphasizes semantic HTML, accessible
responsive design, forms, and interaction patterns. [web.dev
Accessibility](https://web.dev/accessibility/)

Do not claim a site is "fully accessible" merely because a component
library is accessible. End-to-end accessibility still requires research,
design, implementation, and testing. GOV.UK and Atlassian explicitly
make this distinction. [GOV.UK
Accessibility](https://design-system.service.gov.uk/accessibility/) ·
[Atlassian
Accessibility](https://atlassian.design/foundations/accessibility)

# 10. Interaction design

Every interactive control should answer:

-   What is interactive?
-   What will happen?
-   When does it happen?
-   How do I know it worked?
-   What can I do if it failed?

### Interaction state model

``` text
default
→ hover
→ focus-visible
→ pressed/active
→ loading
→ success / updated
→ disabled
→ error
```

### Focus

Use `:focus-visible` where appropriate. Do not remove focus outlines
without replacing them with an equally strong, visible focus treatment.

### Touch

Design touch targets with sufficient size and spacing. Vercel recommends
a minimum 44px touch target for mobile and at least 24px when visual
targets are smaller; Shopify also recommends 44×44px targets for primary
mobile interactions. Treat 44px as a practical baseline for important
touch controls. [Vercel](https://vercel.com/design/guidelines) ·
[Shopify
Accessibility](https://shopify.dev/docs/apps/build/accessibility)

### Forms

Design for:

-   labels
-   helpful defaults
-   autofill
-   validation timing
-   error recovery
-   keyboard navigation
-   loading/submission feedback
-   preserved user input
-   success confirmation

Error messages should describe the problem and the next action when
possible. Vercel's guidance explicitly favors actionable error messages
over merely reporting failure.
[Vercel](https://vercel.com/design/guidelines)

# 11. Motion and animation

Motion should explain relationships, status, or continuity.

Good uses:

-   expanding/collapsing content
-   navigation transitions
-   state changes
-   contextual previews
-   list insertion/removal
-   scroll-linked storytelling when it materially improves comprehension

Avoid:

-   animation for decoration only
-   long delays before interaction becomes usable
-   movement that competes with the primary action
-   infinite motion with no user value
-   animation that blocks content

Use:

``` css
@media (prefers-reduced-motion: reduce) {
  /* reduce or remove non-essential motion */
}
```

Google's Material principles frame motion as a way to preserve
continuity and communicate interaction rather than as decoration.
[Material Design](https://m2.material.io/design/introduction/)

------------------------------------------------------------------------

# 12. Content and UX writing

Write interface copy as part of the design.

Prefer:

-   plain language
-   direct labels
-   short explanatory text
-   descriptive actions
-   progressive disclosure
-   concrete error recovery

Avoid:

-   generic "Continue" when a more descriptive action exists
-   unnecessary jargon
-   walls of text in UI
-   duplicate labels
-   empty marketing claims

Material's communication guidance recommends concise, direct language
that builds trust and clarity. [Google Material
Communication](https://codelabs.developers.google.com/codelabs/material-communication-guidance)

------------------------------------------------------------------------

# 13. Images, video, and art direction

Choose media based on communication needs, not because a section "needs
an image."

For every visual asset, define:

-   role
-   aspect ratio
-   focal point
-   responsive crop
-   alt text requirement
-   loading priority
-   compression format
-   dark/light treatment
-   attribution/license when applicable

Use responsive image delivery:

-   `srcset`
-   `sizes`
-   modern image formats when appropriate
-   explicit dimensions/aspect-ratio to prevent layout shift
-   lazy loading for below-the-fold media

Use video sparingly and respect reduced-motion/autoplay constraints.

------------------------------------------------------------------------

# 14. Performance-first frontend design

Performance is part of visual quality because slow or unstable pages
change perceived quality.

Design for:

-   fast first render
-   stable layout
-   low JavaScript cost
-   efficient images
-   font loading discipline
-   code splitting
-   progressive enhancement
-   minimal blocking work
-   graceful behavior on weak networks/devices

Google currently defines Core Web Vitals around loading performance,
interactivity, and visual stability, with guidance to target good
real-user performance; its current Search documentation lists LCP, INP,
and CLS as the Core Web Vitals. [Google Search Central --- Core Web
Vitals](https://developers.google.com/search/docs/appearance/core-web-vitals)

Use Lighthouse to audit performance, accessibility, SEO, and more.
[Chrome Developers ---
Lighthouse](https://developer.chrome.com/docs/lighthouse/overview)

### Practical frontend defaults

-   server-render when the framework benefits from it
-   hydrate only interactive areas where possible
-   avoid shipping a component library's entire JS payload for a few
    widgets
-   reserve space for media
-   preload only genuinely critical resources
-   use stable skeletons where latency requires them
-   keep layout work predictable
-   measure rather than guessing

# 15. SEO and semantic foundations

Every public page should have:

-   meaningful `<title>`
-   useful meta description when appropriate
-   canonical URL strategy when relevant
-   semantic headings
-   semantic landmarks
-   descriptive link text
-   structured data when it accurately represents the page
-   crawlable content
-   clean URLs
-   Open Graph/social preview metadata when useful
-   correct language metadata

Google Search Essentials groups technical requirements, spam policies,
and best practices as the foundation for eligible search visibility.
[Google Search
Essentials](https://developers.google.com/search/docs/essentials)

# 18. State and data design for app-like sites

  Permissions     allowed, restricted, read-only

-   units
-   date ranges
-   tooltip behavior

# 19. Tables and dense data

Use dense layouts when the task needs them.

Rules:

-   align numerical values consistently
-   use tabular numerals where comparisons matter
-   keep labels visible or programmatically associated
-   provide sorting/filtering labels
-   preserve row/column context on small screens
-   allow horizontal scrolling when a table truly needs width
-   do not shrink text until it becomes hard to read

Vercel recommends tabular numbers for comparisons and explicit handling
of dense/sparse states. [Vercel](https://vercel.com/design/guidelines)

# 20. Navigation patterns

Choose navigation based on information architecture.

### Simple marketing site

Header + CTA + mobile menu.

### Large content site

Header + category nav + search + breadcrumbs + sidebar or TOC.

### Web app

Persistent navigation + contextual sub-navigation + page-level actions.

### Mobile

Prioritize the most frequent tasks. Do not simply collapse desktop
navigation into a tiny hamburger if critical actions become hidden or
discoverability collapses.

# 22. High-quality visual composition checklist

Before calling a design finished, inspect:

### Hierarchy

-   Is the most important thing the most visually obvious thing?
-   Can a user understand the page in a quick scan?
-   Are secondary actions visibly secondary?

### Spacing

-   Are related elements close enough to read as groups?
-   Are unrelated sections sufficiently separated?
-   Is whitespace intentional?

### Typography

-   Is the body copy comfortable to read?
-   Are line lengths controlled?
-   Are headings balanced at every viewport?

### Alignment

-   Do major edges line up?
-   Are cards and controls on consistent baselines?
-   Are icons optically aligned?

### Contrast

-   Is text readable?
-   Does focus stand out?
-   Do disabled/error/success states remain understandable without color
    alone?

### Media

-   Does imagery support the message?
-   Are crops intentional?
-   Is the focal point preserved on mobile?

### Motion

-   Does motion clarify rather than distract?
-   Does the page remain usable with reduced motion?

# 23. QA workflow

Run a structured audit after implementation.

## Pass 1 --- Functional

Check:

-   links
-   buttons
-   forms
-   menus
-   search
-   filters
-   dialogs/drawers
-   route changes
-   loading states
-   error handling

## Pass 2 --- Responsive

Check multiple viewport widths, not just device presets.

Look for:

-   overflow
-   clipped text
-   accidental horizontal scrolling
-   collapsed actions
-   awkward line breaks
-   broken sticky behavior
-   image distortion
-   cramped touch targets

## Pass 3 --- Accessibility

Test:

-   keyboard only
-   focus order
-   screen-reader semantics
-   labels
-   headings
-   link names
-   reduced motion
-   contrast
-   zoom

Use automated tools, but do not treat the score as the whole
accessibility review. Lighthouse itself notes that some audits are
manual and that automated auditing is only part of quality assessment.
[Chrome Developers --- Lighthouse
accessibility](https://developer.chrome.com/docs/lighthouse/accessibility/scoring)

## Pass 4 --- Performance

Measure:

-   LCP
-   INP
-   CLS
-   image weight
-   JS/CSS payload
-   font behavior
-   third-party scripts
-   long tasks

Use real measurements where possible.

## Pass 5 --- Visual polish

Compare against the design intent, not against arbitrary trends.

Ask:

> Does every visual decision support comprehension, trust, identity, or
> interaction?

# 27. How to extract lessons from references

For each reference, write:

``` text
REFERENCE:
WHAT THEY DO:
WHY IT WORKS:
WHAT IS TRANSFERABLE:
WHAT IS BRAND-SPECIFIC:
WHAT WE SHOULD NOT COPY:
```

Example:

``` text
REFERENCE: Apple homepage
WHAT THEY DO: Large focal product storytelling with short copy and clear actions.
WHY IT WORKS: Strong hierarchy limits simultaneous decisions.
TRANSFERABLE: One dominant message per major section; strong visual focal point; clear CTA hierarchy.
BRAND-SPECIFIC: Product imagery, typography, art direction, navigation choices.
DO NOT COPY: Product photography, exact copy, trademark treatment, exact layout, branded assets.
```

# 36. Anti-noise visual discipline

This section is a non-negotiable frontend craft rule for generated or
hand-built interfaces.

The goal is not to make every site empty or sterile. The goal is to
prevent accidental visual residue, ornamental filler, repeated
micro-details, and template-like decoration from making the interface
feel machine-generated.

## 36.1 Do not add decorative noise by default

Do not automatically add:

-   decorative horizontal rules beside headings or eyebrow labels
-   repeated dots, stars, diamonds, sparkles, crosses, or separator
    glyphs
-   random vertical bars or tiny divider marks
-   decorative circles, rings, badges, stamps, seals, or floating
    stickers
-   fake handwritten notes, pseudo-editorial labels, or arbitrary
    coordinates
-   repeated "premium", "crafted", "curated", or similar micro-copy that
    adds no information
-   ornamental arrows appended to ordinary links
-   unnecessary gradients, glows, grain, blobs, noise textures, or
    background shapes
-   tiny underlines, overlines, accent strokes, or corner marks used
    only to make a section look designed
-   repeated pill badges when simple text communicates the same thing
-   icon-only decoration beside already-clear text
-   arbitrary monograms, initials, decorative numbers, or symbols that
    were not requested
-   visual elements copied from generic AI landing-page patterns merely
    because they fill empty space

### Core rule

> If a visual detail does not improve comprehension, hierarchy,
> identity, interaction, accessibility, or useful atmosphere, remove it.

Do not insert decoration merely because an area feels empty.

Whitespace is not a problem to solve automatically. Empty space can
establish hierarchy, pacing, focus, and confidence. Atlassian's current
spacing guidance treats whitespace, proximity, hierarchy, visual rhythm,
and optical adjustment as meaningful design tools. [Atlassian Design ---
Spacing](https://atlassian.design/foundations/spacing)

## 36.2 AI-looking residue audit

Before finalizing a page, scan every viewport for details that look like
leftover generation artifacts.

Ask:

``` text
Would a real designer intentionally keep this?
Does it communicate something?
Would removing it change the user's understanding or action?
Is it repeated only because a template expects it?
Does it compete with the primary hierarchy?
Does it look like decoration added after the design was already complete?
```

Remove the element when the answer is consistently "no useful purpose."

Pay particular attention to:

``` text
heading → tiny line
heading → tiny dot
heading → badge
card → random icon
card → random number
button → decorative arrow
section → repeated ornamental separator
empty space → floating blob
image → unnecessary badge/sticker
footer → excessive micro-labels
```

These patterns are not forbidden in all designs. They are forbidden as
unexamined defaults.

## 36.3 Preserve structure, remove ornament

Do not confuse decorative cleanup with removing useful structure.

Keep elements that provide:

-   grouping
-   hierarchy
-   navigation
-   affordance
-   form guidance
-   status
-   wayfinding
-   brand identity
-   meaningful rhythm
-   accessibility information
-   content separation that would otherwise become ambiguous

The standard is purpose, not "never use lines" or "never use dots."

## 36.4 One visual language per decision

Avoid mixing unrelated visual signals.

If the page already has strong typography, generous whitespace,
restrained borders, editorial photography, and one meaningful accent
color, do not automatically add floating badges, gradient blobs,
glassmorphism, grain, decorative symbols, multiple shadow styles, or
several corner-radius families.

A polished interface often feels refined because fewer visual systems
compete at once.

Apple's current design guidance describes simplicity as removing what is
unnecessary while retaining enough context for clarity. It describes
craft as attention to detail, typography, graphics, responsive
animation, and iterative refinement rather than decorative effects added
at the end. [Apple --- Principles of great design,
WWDC26](https://developer.apple.com/videos/play/wwdc2026/250/)

## 36.5 Avoid filler symmetry

Do not add elements simply to make columns look equally occupied.

If content does not need an icon, number, badge, or label, do not add
one for visual balance.

Related components should share a system, but they do not need identical
decoration when their content has different roles.

Atlassian's current guidance recommends visual hierarchy, proximity, and
varied rhythm so that all elements do not receive the same visual
importance. [Atlassian Design ---
Spacing](https://atlassian.design/foundations/spacing)

## 36.6 Copy cleanup is visual cleanup

Treat copy and punctuation as visual material.

Avoid decorative or repetitive patterns such as:

``` text
Title · Subtitle
Title — premium experience
Label ✦ Label ✦ Label
Read more →
Made with care • Built with purpose
```

unless that punctuation or symbol is genuinely part of the established
brand language.

Prefer direct language and normal punctuation. Vercel's current
guidelines emphasize concise content, clear labels, natural language,
meaningful status cues, and tidy line breaks/rag. [Vercel Web Interface
Guidelines](https://vercel.com/design/guidelines)

## 36.7 Decorative detail budget

Every page should have a limited visual detail budget.

Before adding a decorative treatment, identify:

``` text
PURPOSE:
What does this detail accomplish?

LOCATION:
Why is it needed here?

SYSTEM:
What existing design token/pattern does it belong to?

FREQUENCY:
Why does it appear this many times?

EXIT:
What would break if it were removed?
```

If these questions cannot be answered, do not add the detail.

This applies to CSS as well as HTML: pseudo-elements, masks, gradients,
shadows, absolute-positioned accents, background decorations, repeated
SVG ornaments, animation loops, and decorative transitions.

Prefer one strong treatment over many small effects.

# 37. Frontend finishing craft: how developers tune the final 10%

The first implementation is not the finished design.

A professional frontend process contains a dedicated tuning pass after
structure and functionality are working.

Use:

``` text
BUILD
→ VERIFY
→ TUNE
→ REMOVE
→ POLISH
→ TEST
→ SHIP
```

Do not treat the first visually acceptable render as final.

## 37.1 Pass A --- establish the raw composition

First make the page structurally correct:

-   semantic HTML
-   layout grid
-   content order
-   responsive behavior
-   type scale
-   component states
-   interactions
-   media
-   accessibility

Do not spend time polishing shadows or micro-spacing while hierarchy is
still wrong.

## 37.2 Pass B --- tune hierarchy

At each major viewport, ask:

``` text
What do I notice first?
What do I notice second?
Where does my eye stop?
What is the primary action?
What can safely become quieter?
```

Tune in this order:

1.  content order
2.  type scale
3.  width and reading measure
4.  whitespace
5.  contrast
6.  alignment
7.  component treatment
8.  decoration

Apple's current guidance emphasizes purpose, clarity, hierarchy, and
craft; strong hierarchy uses order, spacing, and contrast to make the
most important content obvious. [Apple --- Principles of great design,
WWDC26](https://developer.apple.com/videos/play/wwdc2026/250/)

## 37.3 Pass C --- tune spacing optically

Do not trust a spacing token blindly.

Start from the token system, then make small optical adjustments when
visual weight demands them.

Inspect logo-to-wordmark spacing, heading-to-paragraph spacing,
heading-to-media spacing, button-to-button gap, card image-to-content
gap, section-to-section rhythm, line-height, baseline alignment, and
asymmetrical visual weight.

The goal is perceived balance, not mathematical sameness.

Atlassian specifically recommends optical adjustment after establishing
a spacing system because visual weight can require small deviations from
standard spacing values. [Atlassian Design ---
Spacing](https://atlassian.design/foundations/spacing)

## 37.4 Pass D --- tune typography like a craftsperson

Typography is one of the highest-leverage finishing tools.

Check:

-   font rendering
-   weight contrast
-   line-height
-   character density
-   heading wraps
-   orphan/widow lines
-   body measure
-   button label fit
-   metadata size
-   punctuation
-   capitalization
-   numerals
-   optical alignment

Do not solve every hierarchy problem by increasing font size. Use width,
weight, spacing, tone, and placement as well.

Vercel's current guidelines explicitly call for tidy line breaks/rag and
resilience to short, average, and long content. Atlassian's typography
guidance emphasizes readability, visual hierarchy, and visual harmony.
[Vercel Web Interface Guidelines](https://vercel.com/design/guidelines)
[Atlassian Design ---
Typography](https://atlassian.design/foundations/typography)

## 37.5 Pass E --- tune borders, radius, and shadows

These details should make the material hierarchy believable.

Check:

-   border visibility
-   border hue
-   border thickness
-   nested radius alignment
-   shadow softness
-   shadow direction
-   whether elevation is actually needed
-   whether cards look like cards or like floating boxes without reason

Avoid assigning a different shadow to every component. Avoid a different
radius for every component.

Vercel's current design guidance recommends crisp borders, coherent hue
treatment, layered shadows, and nested radii. [Vercel Web Interface
Guidelines](https://vercel.com/design/guidelines)

## 37.6 Pass F --- tune interactions

For each interactive element, verify:

``` text
default
hover
focus-visible
pressed
disabled
loading
success/updated
error
```

The states should feel like the same component changing state, not
separate designs.

Tune response speed, movement distance, contrast change, focus
visibility, pressed depth, text movement, icon movement, loading
indicator behavior, and success acknowledgement.

Do not add motion simply to prove that animation exists.

Vercel emphasizes visible focus, keyboard operation, state coverage, and
clear content behavior. [Vercel Web Interface
Guidelines](https://vercel.com/design/guidelines)

## 37.7 Pass G --- tune motion

Motion should feel quiet, immediate, and contextual.

For every animation define:

``` text
TRIGGER
DURATION
EASING
DISTANCE
OPACITY
LOOP
EXIT
REDUCED-MOTION BEHAVIOR
```

Use transform/opacity for most small UI movement where possible.

For animated elements, verify that motion does not distract from the
primary action, cause layout shift, trap attention, create a perpetual
visual tax, reduce readability, or become annoying after repeated
exposure.

For continuous animation, ask:

> Would a person still be comfortable looking at this page after several
> minutes?

Use `prefers-reduced-motion` and remove or substantially reduce
non-essential motion.

Apple currently frames motion as part of crafted, responsive
interaction, while web.dev recommends smooth animation and attention to
animation performance. [Apple --- Principles of great design,
WWDC26](https://developer.apple.com/videos/play/wwdc2026/250/) [web.dev
--- animation examples](https://web.dev/examples/images)

## 37.8 Pass H --- remove before adding

After polishing, perform a reverse pass.

Look for:

``` text
line
dot
badge
icon
shadow
gradient
border
label
arrow
background shape
animation
```

For every one ask:

``` text
Does the page become clearer without it?
```

When the answer is yes, delete it.

This "remove before adding" pass is essential because generated
interfaces can accumulate small embellishments faster than they
accumulate judgment.

## 37.9 Pass I --- inspect at real browser sizes

Do not finish from one desktop screenshot.

Inspect at minimum:

``` text
small mobile
large mobile
tablet
compact desktop
desktop
wide desktop
```

Also test long text, short text, browser zoom, keyboard navigation,
reduced motion, slower network, missing media, failed form submission,
empty states, and error states.

A polished page is one that remains visually coherent when conditions
change.

## 37.10 Pass J --- compare adjacent regions

Compare neighboring sections instead of only the full page.

Check:

``` text
hero → next section
section heading → content
image → text
card → card
header → page body
body → footer
```

Look for accidental alignment breaks, inconsistent spacing, competing
focal points, repeated decorative patterns, overly mechanical rhythm,
abrupt type changes, excessive borders, visual dead zones, and crowded
transitions.

# 38. Developer teaching protocol: explain and tune frontend design

When teaching a developer how to create high-quality frontend design, do
not teach "add more effects."

Teach the reasoning loop:

``` text
1. Identify the purpose.
2. Establish hierarchy.
3. Build the simplest structure that can support it.
4. Add the design system.
5. Make the content fit the system.
6. Test real content.
7. Tune spacing and typography.
8. Tune component states.
9. Remove unnecessary decoration.
10. Verify responsiveness and accessibility.
11. Measure performance.
12. Perform one final visual cleanup pass.
```

## 38.1 Teach decisions, not recipes

Teach developers to explain why a radius, border, shadow, gradient,
badge, icon, or animation exists instead of prescribing decoration by
default.

A premium effect should be the result of a communication or brand need,
not a generic "make it look better" step.

## 38.2 Use the "why this exists" test

For every non-trivial visual element, the developer should be able to
explain:

``` text
WHY:
Why does this exist?

WHAT:
What does it communicate?

RELATION:
What does it relate to?

STATE:
How does it behave?

RESPONSIVE:
What happens when space changes?

ACCESSIBILITY:
Does it remain understandable without color, hover, or motion?

REMOVAL:
What would improve if it disappeared?
```

If the developer cannot answer these questions, reconsider the element.

## 38.3 Teach visual debugging in order

When something looks wrong, debug in this order:

``` text
1. Content problem
2. Hierarchy problem
3. Layout problem
4. Spacing problem
5. Typography problem
6. Color/contrast problem
7. Component treatment problem
8. Motion problem
9. Decorative detail problem
```

Do not immediately add CSS.

A wrong layout cannot be repaired by a shadow. A weak hierarchy cannot
be repaired by a gradient. An awkward section cannot be repaired by a
badge.

## 38.4 Teach one-variable tuning

When refining a frontend, change a small set of related variables at a
time.

Example:

``` text
Round 1:
heading size + line-height + max-width

Round 2:
section spacing + internal gaps

Round 3:
border + radius + shadow

Round 4:
button height + padding + label weight

Round 5:
motion duration + easing
```

Then inspect again.

This makes visual causality easier to understand than changing twenty
unrelated CSS values at once.

## 38.5 Teach visual before/after comparison

For meaningful polish work, capture or inspect:

``` text
BEFORE
→ structural issue
→ visual change
→ AFTER
→ reason for change
```

Do not praise a change merely because it "looks nicer."

Explain what improved:

-   clearer hierarchy
-   easier scanning
-   stronger alignment
-   less visual competition
-   more believable spacing
-   more coherent component language
-   fewer distracting details
-   improved interaction feedback

## 38.6 Teach final-touch vocabulary

Developers should learn to identify:

``` text
optical alignment
visual weight
reading measure
baseline alignment
content rhythm
hierarchy
density
contrast
affordance
material boundary
micro-spacing
state feedback
motion continuity
visual noise
focal point
responsive composition
```

Use these concepts to diagnose what is happening rather than relying on
vague phrases such as "make it more premium."

# 39. Final frontend cleanup checklist

Before calling a generated interface finished, perform this explicit
check.

### Remove

-   unnecessary lines
-   unnecessary dots
-   unnecessary stars
-   unnecessary arrows
-   unnecessary badges
-   unnecessary numbers
-   unnecessary icons
-   duplicate labels
-   repeated micro-copy
-   arbitrary shapes
-   unused decorative pseudo-elements
-   excessive shadows
-   excessive gradients
-   excessive pills
-   ornamental animation
-   placeholder content that looks production-like

### Tune

-   heading wraps
-   body line length
-   vertical rhythm
-   section spacing
-   alignment
-   baseline relationships
-   image crop
-   card density
-   button proportions
-   border contrast
-   radius relationships
-   hover/focus/pressed states
-   motion timing
-   reduced-motion behavior
-   mobile composition

### Verify

-   does the hierarchy read immediately?
-   does every visual detail have a reason?
-   does anything feel leftover?
-   does anything look generated just to fill space?
-   are repeated elements actually useful?
-   is whitespace working?
-   does the interface still feel coherent with decoration removed?
-   does the page survive realistic content and viewport changes?
-   does the visual treatment reinforce the brand rather than distract
    from it?

## 39.1 The final-touch principle

> **Do not finish by adding. Finish by editing.**

The strongest final pass often removes small details, corrects
proportions, improves spacing, fixes typography, aligns components,
simplifies copy, and makes interaction states feel natural.

That is frontend craft.

# 41. Professional font selection and typography engineering

Typography is a design system decision, not a decorative afterthought.

A professional frontend developer does not begin with "What font looks
cool?" They begin with:

``` text
What does the product need typography to accomplish?
```

Then choose the smallest typography system that satisfies those needs.

## 41.1 Start with typographic roles

Define roles before choosing families:

``` text
DISPLAY
Hero statements, brand expression, major editorial headings

HEADING
Section titles and content hierarchy

BODY
Readable paragraphs and explanatory content

UI
Navigation, controls, buttons, labels, forms

DATA
Tables, prices, metrics, timestamps, technical values

UTILITY
Metadata, captions, legal text, secondary context
```

One family can perform several roles. A second family is justified only
when the contrast creates a meaningful improvement in brand expression
or hierarchy.

Apple's typography guidance recommends minimizing the number of
typefaces and using weight, size, and color to express hierarchy. It
also cautions against overly light weights for legibility. [Apple ---
Typography](https://developer.apple.com/design/human-interface-guidelines/typography)
[Apple --- Principles of great
design](https://developer.apple.com/videos/play/wwdc2026/250/)

## 41.2 Professional font-selection sequence

Use this sequence:

``` text
1. Product/brand personality
2. Audience and reading environment
3. Language/script coverage
4. Glyph quality
5. Readability at intended sizes
6. Available weights/styles/widths
7. Numerals and punctuation
8. Variable-font capabilities when useful
9. Rendering across target browsers/devices
10. Licensing
11. File size and loading cost
12. Fallback behavior
```

Do not choose a font because it is currently fashionable.

## 41.3 Evaluate the actual glyphs

Test the letters and symbols that appear in the product.

At minimum inspect:

``` text
Aa
Qq
Gg
Rr
01 23 45 67 89
₹ $ € £
“ ” ‘ ’
& @ #
```

For editorial or multilingual products, also test real copy rather than
a pangram alone.

Look for:

-   shape consistency
-   counters
-   x-height
-   stroke contrast
-   terminal design
-   punctuation quality
-   numeral proportions
-   italic behavior
-   bold behavior
-   spacing at actual UI sizes

The font should look good in the actual interface, not only in a
specimen page.

## 41.4 Pairing fonts professionally

When two families are used, give them distinct responsibilities.

Good pairing logic:

``` text
SERIF DISPLAY + SANS UI
EDITORIAL HEADING + NEUTRAL BODY
EXPRESSIVE BRAND FONT + QUIET UTILITY FONT
```

Bad pairing logic:

``` text
decorative font + decorative font
high-contrast display + high-contrast UI
three or four competing families
```

Before adding a second family, test whether one family with weight,
size, tracking, and spacing can already create the hierarchy.

Apple recommends minimizing typefaces because too many can obscure
hierarchy and reduce internal consistency. citeturn436232search3

## 41.5 Choose weights deliberately

Do not load every available weight.

Select the minimum useful set, for example:

``` text
400 — body
500 — secondary emphasis / UI
600 — headings / controls
700 — strong emphasis
```

This is an example, not a fixed prescription.

The correct set depends on the typeface and product.

Avoid extremely thin weights for small text unless they remain clearly
legible in real conditions. Apple explicitly recommends avoiding
ultralight, thin, and light weights when legibility suffers.
citeturn436232search3

## 41.6 Choose optical scale, not arbitrary size

When defining a type scale, inspect:

``` text
size
weight
line-height
letter-spacing
max-width
contrast
relationship to nearby content
```

A 64px heading is not automatically better hierarchy than a 48px
heading.

Tune the complete typographic lockup.

For large display text, adjust line-height and max-width together
because line wrapping strongly changes perceived hierarchy.

## 41.7 Readability beats fashionable typography

Check:

-   body text at actual device size
-   long paragraphs
-   labels next to controls
-   low-light and high-brightness conditions
-   zoom
-   different browsers
-   different operating systems
-   small metadata
-   numerals
-   punctuation
-   mixed-case reading

Keep body measure controlled. Avoid very long lines simply because a
wide screen allows them.

## 41.8 Font loading is part of visual quality

Typography can change layout and therefore affect perceived polish and
Core Web Vitals.

Use:

-   WOFF2 for modern webfont delivery where self-hosting
-   font subsetting when the language/content set is known
-   `unicode-range` where useful
-   appropriate `font-display`
-   preload only genuinely critical fonts after measurement
-   fallback stacks that are metrically compatible where practical

web.dev notes that webfonts can delay text rendering and can create
layout shifts when fallback and final fonts differ. It recommends
careful loading strategy, WOFF2, fewer fonts, and appropriate
`font-display`. [web.dev --- Best practices for
fonts](https://web.dev/articles/font-best-practices) [MDN --- CSS
performance](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Performance/CSS)

Do not preload every font weight.

A useful default is to start with the smallest set of critical faces and
measure before adding more.

## 41.9 Google Fonts and hosted fonts

When using a hosted font service, consider:

``` text
network connection cost
font CSS discovery
font subsets
display strategy
privacy/project requirements
licensing
cache behavior
```

Google's documentation notes that text-specific requests can
substantially reduce downloaded font data when the exact character set
is known. [Google Fonts
API](https://developers.google.com/fonts/docs/getting_started)

Do not optimize fonts blindly. Measure the actual page.

## 41.10 Variable fonts

Use variable fonts when they provide a meaningful benefit, such as:

-   one resource replacing several static styles
-   controlled weight variation
-   width adjustment
-   optical sizing
-   responsive typography

Do not use variable axes merely because the font exposes them.

Every additional axis should have a design reason.

## 41.11 Typography QA matrix

Before shipping, test:

``` text
Short heading
Long heading
Single-line heading
Two-line heading
Three-line heading

Short body
Normal paragraph
Long paragraph

Short button
Long button

Small number
Large number
Currency
Date
```

Then inspect every target viewport.

A type system is successful when realistic content remains intentional.

# 42. Professional animation selection and motion engineering

Animation should be treated like interaction design, not visual
decoration.

The professional question is:

``` text
What relationship, state, cause, or feeling does this motion communicate?
```

If the answer is "nothing," do not animate it.

Apple says custom motion should be purposeful, precise, optional, and
brief enough not to dominate the experience. Vercel's current web
guidelines similarly recommend CSS-first animation, compositor-friendly
properties, purposeful motion, appropriate easing, correct transform
origins, and reduced-motion variants.
citeturn436232search4turn805173search0

## 42.1 Classify motion before implementing it

Choose a motion category:

``` text
FEEDBACK
Button pressed, saved state, validation

TRANSITION
Panel opens, page region changes, navigation state changes

CONTINUITY
An element moves between related states or locations

DISCOVERY
A subtle entrance helps reveal new content

AMBIENCE
Non-essential environmental motion used sparingly for brand atmosphere
```

Ambience has the strictest restraint requirement.

## 42.2 Choose motion from the object

The object determines the motion language.

Examples:

``` text
STEAM
soft, irregular, buoyant, low-amplitude drift

DROPDOWN
short vertical reveal from its origin

MODAL
quick entry from the point of invocation

TOAST
short slide/fade with clear arrival and exit

BUTTON
tiny scale/position/contrast response

IMAGE HOVER
small scale shift with controlled easing

PAGE TRANSITION
brief continuity between related states
```

Do not use one generic "ease-in-out" animation for everything.

Vercel explicitly recommends choosing easing based on what changes and
anchoring motion to the element's physical origin.
citeturn805173search0

## 42.3 Choose duration by distance and frequency

Use the minimum duration that communicates the change.

Think relationally:

``` text
tiny change
→ very short motion

small contextual transition
→ short motion

larger spatial transition
→ somewhat longer motion

frequent interaction
→ especially quick and quiet

continuous ambient loop
→ slow enough to feel organic, but never attention-seeking
```

Do not create fixed "300ms everywhere" rules.

The duration depends on distance, frequency, complexity, and importance.

## 42.4 Choose easing from physical intent

A useful reasoning model:

``` text
EASE-OUT
For something arriving and settling.

EASE-IN
For something departing or accelerating away.

EASE-IN-OUT
For reversible travel between two stable states.

LINEAR
For continuous cycles where constant speed is perceptually appropriate.

CUSTOM CURVE
When the material or emotional behavior requires a specific feel.
```

This is a starting model, not a law.

Tune the curve by actually watching the result at normal usage speed.

## 42.5 Use transform and opacity first

For small UI motion, prefer:

``` css
transform
opacity
```

Avoid animating layout properties such as:

``` css
width
height
top
left
margin
padding
```

when a transform-based solution can achieve the same visual result.

Vercel specifically recommends compositor-friendly properties and
avoiding layout-triggering animation. citeturn805173search0

## 42.6 Use the correct transform origin

A transition should originate from the object's perceived physical
anchor.

Examples:

``` text
dropdown → top edge
popover → point near trigger
scale-up card → visual center
steam → lower origin near the cup
rotation icon → its center
```

For SVG, place animation on a `<g>` wrapper and set an explicit
transform box/origin where necessary. Vercel specifically calls out SVG
transform-origin consistency and recommends grouped transforms for
cross-browser reliability. citeturn805173search0

## 42.7 Continuous animation requires a higher bar

Infinite animation can become an ongoing visual tax.

Before shipping a loop, verify:

``` text
Is it useful?
Is it subtle?
Does it compete with content?
Does it have a natural cycle?
Does the loop have a visible seam?
Does the user have to watch it?
Does it remain comfortable after several minutes?
Can it stop or reduce under accessibility settings?
```

A brand mark such as COFUA's steam can justify continuous ambient motion
because it expresses the subject of the brand. But it should remain
subordinate to navigation and content.

Do not put continuous motion on many independent elements
simultaneously.

## 42.8 Build loops to avoid seams

For an infinite loop:

``` text
state A
→ state B
→ state C
→ state B'
→ state A
```

is often more natural than:

``` text
A
→ B
→ A
```

for organic materials.

Use asymmetry, phase offsets, scale changes, opacity variation, and
non-identical cycles when they improve realism.

Never create complexity merely to create complexity.

## 42.9 Stagger with intent

Stagger can explain sequence or create organic variety.

Use it for:

-   list entry
-   multi-part reveal
-   related elements with a logical order
-   independent ambient elements

Avoid stagger on every section or every card. Repeated stagger becomes
predictable and can feel like a template.

## 42.10 Motion should not move layout

A visual transition should not cause content to jump unexpectedly.

Prefer:

``` text
transform
opacity
clip-path/masks when measured and justified
```

with stable dimensions/reserved space where possible.

Measure layout stability rather than assuming it is fine.

## 42.11 Reduced motion is a designed state

Do not simply "turn animation off."

Define the reduced-motion alternative:

``` text
animated reveal → instant reveal
large translation → opacity-only or no motion
parallax → static positioning
ambient loop → still frame
animated emphasis → stronger static contrast
```

Use:

``` css
@media (prefers-reduced-motion: reduce) {
  /* provide the deliberate reduced-motion state */
}
```

Vercel explicitly requires a reduced-motion variant, and Apple stresses
that motion should be optional and not be the only channel for important
information. citeturn805173search0turn436232search4

## 42.12 Professional motion testing

Test animation:

``` text
normal speed
slow-motion inspection
repeated interaction
reduced-motion
keyboard interaction
touch interaction
low-powered device
background tab
different browsers
```

During slow-motion inspection, look for:

-   jumps
-   overshoot
-   awkward transform origin
-   inconsistent acceleration
-   opacity disappearing too early
-   elements feeling disconnected
-   text becoming blurry during scale
-   loop seams
-   accidental layout shift

The slow inspection is especially useful because imperfections hidden at
normal speed become obvious.

# 43. Design-token guidance for type and motion

Treat typography and motion as first-class design tokens.

Example:

``` css
:root {
  /* type */
  --font-ui: ...;
  --font-display: ...;
  --weight-regular: 400;
  --weight-medium: 500;
  --weight-semibold: 600;
  --weight-bold: 700;

  --leading-tight: ...;
  --leading-body: ...;
  --tracking-tight: ...;

  /* motion */
  --duration-instant: ...;
  --duration-fast: ...;
  --duration-normal: ...;
  --duration-slow: ...;

  --ease-standard: ...;
  --ease-out: ...;
  --ease-in: ...;
  --ease-emphasized: ...;
}
```

Use tokens to create consistency, then make optical adjustments when the
component genuinely needs them.

Do not turn the token system into a rigid mathematical prison.

# 44. Professional designer/developer decision loop

When a frontend needs a font or animation, use this decision loop:

``` text
OBSERVE
What problem exists?

DEFINE
What should the user perceive?

SELECT
What typography or motion behavior best communicates it?

IMPLEMENT
Use the smallest reliable technical solution.

TEST
Check realistic content and real devices.

TUNE
Adjust size, weight, spacing, duration, easing, origin, or amplitude.

REMOVE
Delete anything that still feels unnecessary.

VERIFY
Accessibility + responsiveness + performance + visual coherence.
```

This is the preferred workflow over choosing fonts and animations from
trend lists.

# 46. Agent execution protocol for maximum frontend output quality

For agents generating frontend code, apply the following sequence on
every substantial design task:

``` text
1. UNDERSTAND
   Determine audience, task, business goal, content hierarchy, constraints.

2. RESEARCH
   Inspect relevant authoritative design-system, accessibility,
   browser, performance, and typography references.

3. DISTILL
   Write:
   Keep / Avoid / Adapt / Prove.

4. ARCHITECT
   Define page map, layout, component system, responsive behavior,
   states, typography, imagery, motion, and validation plan.

5. BUILD
   Implement semantic, reusable, content-driven frontend structure.

6. VERIFY
   Confirm interaction, responsiveness, accessibility, and functional behavior.

7. TUNE TYPE
   Test real copy, heading wraps, line length, weights, numerals,
   fallback behavior, and font loading.

8. TUNE MOTION
   Define purpose, trigger, duration, easing, origin, amplitude,
   interruptibility, reduced-motion behavior, and performance.

9. REMOVE NOISE
   Delete decorative lines, dots, stars, arbitrary badges, filler icons,
   redundant labels, ornamental arrows, unnecessary gradients,
   excessive pills, and other residue unless each has a clear purpose.

10. POLISH
    Tune optical alignment, spacing, typography, borders, radius,
    image crops, control proportions, and interaction feedback.

11. QA
    Test multiple viewport widths, zoom, keyboard, reduced motion,
    realistic content, slow/network-constrained conditions,
    and browser differences.

12. FINAL EDIT
    Ask:
    “What is the smallest set of visual decisions that makes this
    experience feel complete, intentional, and human?”
```

The agent must **not stop after the first successful render**.

It should assume a final visual-editing pass is required.

Before returning frontend code, the agent should answer internally:

- Are there too many typefaces?
- Are the weights justified?

- Is loading behavior acceptable?

MOTION

# 49. Evidence, assumptions, and research integrity

AI-generated frontend work can look plausible while quietly containing
invented facts or unsupported claims. Production-grade work must
separate fact, inference, assumption, and placeholder content.

## 49.1 Label information by confidence

Use this mental model:

``` text
USER-PROVIDED
Directly supplied by the user or source material.

VERIFIED
Confirmed through an appropriate authoritative source.

INFERRED
A design/engineering inference based on available evidence.

ASSUMED
A temporary implementation assumption.

PLACEHOLDER
Intentionally non-production content awaiting real information.
```

Never present `ASSUMED`, `INFERRED`, or `PLACEHOLDER` information as
verified fact.

## 49.2 Research only when it changes the decision

Search the web when the request depends on:

-   current platform behavior
-   current browser/frontend guidance
-   current standards
-   current vendor documentation
-   current design-system patterns
-   changing software APIs
-   current performance guidance
-   niche or uncertain technical details

Do not browse merely to add citations or decorative references.

## 49.3 Source hierarchy

Prefer:

``` text
official product/vendor documentation
→ standards bodies
→ established design systems
→ reputable technical education
→ specialist community references
→ inspiration galleries
```

Use inspiration sources for visual discovery, not as authoritative
technical evidence.

## 49.4 Research synthesis

Do not paste research into the design process.

Convert it to:

``` text
FACT:
What the source actually establishes.

DESIGN IMPLICATION:
How that fact changes the interface decision.

IMPLEMENTATION IMPLICATION:
What the developer should do in code.

LIMITATION:
What the source does not establish.

DECISION:
What we will use for this project.
```

This keeps research useful instead of turning the skill into a citation
dump.

# 50. Agent conflict-resolution protocol

When instructions, references, or implementation details conflict,
resolve them in this order:

``` text
1. Explicit user requirement
2. Safety and legal/platform constraints
3. Accessibility/standards requirements
4. Content truthfulness
5. Functional requirements
6. Responsive/layout requirements
7. Design-system consistency
8. Visual preferences
9. Decorative preferences
```

If a requested visual treatment would harm accessibility, performance,
responsiveness, or task completion, adapt the treatment rather than
blindly reproducing it.

When a reference conflicts with a user's actual content or constraints,
the user's actual brief wins.

# 51. Production frontend implementation contract

For generated code, optimize for code that another developer can safely
maintain.

## 51.1 Semantic structure first

Use:

``` text
header
nav
main
section
article
aside
footer
button
a
form
label
input
```

according to their actual semantic role.

Do not use `<div>` for every structure merely because it is convenient.

## 51.2 CSS architecture

Prefer:

``` text
tokens
→ base styles
→ layout primitives
→ reusable components
→ states
→ responsive overrides
→ page composition
```

Avoid long chains of selector overrides that make a component's final
appearance difficult to understand.

## 51.3 Avoid magic numbers

A one-off value can be correct, especially for optical adjustment, but
it should be explainable.

Prefer:

``` css
var(--space-...)
var(--radius-...)
var(--duration-...)
var(--color-...)
```

for repeated decisions.

Use one-off values when they solve a real optical or content problem,
not because the agent did not establish a system.

## 51.4 Keep interaction logic local

Prefer the simplest state ownership that works.

Do not create application-wide state for a local interaction.

Do not add a state library when native HTML, CSS, or a small local
controller is enough.

## 51.5 Progressive enhancement

Ask:

``` text
What should still work with JavaScript unavailable?
What can load before hydration?
What can be semantic HTML instead of scripted UI?
```

For content-heavy pages and simple interactions, preserve useful
functionality through native platform behavior where practical.

## 51.6 Native browser behavior is a feature

Use native capabilities when they already provide:

-   keyboard navigation
-   focus management
-   form validation
-   semantic behavior
-   scrolling
-   disclosure
-   dialog behavior
-   loading semantics

Do not recreate browser behavior unnecessarily.

# 52. Production responsive engineering

Responsive design is not a set of screenshot breakpoints. It is a system
for preserving hierarchy as available space changes.

## 52.1 Test content pressure

Every important component should survive:

``` text
short content
normal content
long content
localized content
large text
zoomed viewport
missing optional content
```

Do not design only for ideal marketing copy.

## 52.2 Prefer fluid behavior before breakpoint overrides

Start with:

``` text
intrinsic sizing
flex/grid
min/max/clamp
content wrapping
container-aware constraints
```

then add media/container queries only where the composition actually
changes.

## 52.3 Breakpoints are behavioral changes

A breakpoint should answer:

``` text
What becomes impossible or undesirable at this width?
```

Examples:

``` text
navigation links no longer fit
two-column reading measure becomes too narrow
product cards lose useful width
actions need reprioritization
media crop becomes inappropriate
```

Do not add breakpoints merely because common device presets exist.

## 52.4 Safe-area and viewport behavior

For full-bleed or fixed UI, consider:

``` css
env(safe-area-inset-top)
env(safe-area-inset-right)
env(safe-area-inset-bottom)
env(safe-area-inset-left)
```

when appropriate.

Test:

-   mobile browser UI expansion/collapse
-   landscape
-   keyboard appearance
-   notches/cutouts
-   sticky headers
-   fixed footers
-   nested scrolling

# 53. Production accessibility gates

Accessibility is a release criterion, not optional polish.

## 53.1 Hard requirements

Before release, verify:

``` text
semantic structure
keyboard operation
visible focus
focus not obscured
logical focus order
labels
accessible names
status announcements where needed
contrast
text resize/zoom
target size/spacing
reduced motion
non-color status communication
```

WCAG 2.2 establishes the conformance baseline; use it as the normative
accessibility reference. Additional systems such as APCA can be used as
supplementary perceptual guidance but must not replace WCAG conformance
testing.

WCAG 2.2 includes a 24 × 24 CSS pixel minimum target-size criterion for
pointer inputs with defined exceptions. Larger targets such as 44 × 44
CSS pixels remain a practical usability baseline for primary mobile
controls used by major design systems. [W3C WCAG
2.2](https://www.w3.org/TR/wcag/) [Vercel Web Interface
Guidelines](https://vercel.com/design/guidelines)

## 53.2 Focus behavior

Verify that:

-   focus is always visible
-   sticky UI does not cover the focused control
-   focus moves logically
-   dialogs manage focus correctly
-   opening and closing overlays returns focus appropriately
-   focus is never dependent on animation completion

W3C and current design-system guidance both emphasize visible,
unobscured focus. [W3C WCAG 2.2](https://www.w3.org/TR/wcag/) [Vercel
Web Interface Guidelines](https://vercel.com/design/guidelines)

## 53.3 Reduced-motion behavior

Do not simply remove all motion without considering meaning.

Define an alternative for meaningful transitions:

``` text
movement → fade
parallax → static
ambient loop → still state
large spatial transition → short dissolve
```

Apple and Atlassian both emphasize designing motion as an intentional,
accessible system rather than simply sprinkling effects across a page.
[Apple --- Reduced
Motion](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/reduced-motion-evaluation-criteria)
[Atlassian Design ---
Motion](https://atlassian.design/foundations/motion)

# 54. Production performance gates

Performance is part of the visual experience.

## 54.1 Core signals

Measure, where applicable:

``` text
LCP
INP
CLS
```

Also inspect:

``` text
font transfer size
image transfer size
JavaScript execution
long tasks
layout shifts
third-party scripts
render-blocking resources
```

Google's current Core Web Vitals guidance centers on LCP, INP, and CLS
as the primary user-centric metrics for loading performance,
responsiveness, and visual stability. [Google Search Central --- Core
Web
Vitals](https://developers.google.com/search/docs/appearance/core-web-vitals)

## 54.2 Animation performance

Prefer properties that can remain efficient:

``` text
transform
opacity
```

Be cautious with animations that force layout or expensive repaint work.

MDN notes that animation cost varies by property and that expensive
animation can produce jank; it recommends performance-aware animation
techniques. [MDN --- Animation performance and frame
rate](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Animation_performance_and_frame_rate)

## 54.3 Font performance

Use only the faces/weights/scripts needed by the actual product.

Where appropriate:

``` text
WOFF2
subsetting
unicode-range
font-display
careful preloading
compatible fallback fonts
```

Do not preload every font or weight.

## 54.4 Images and video

Prefer:

``` text
correct dimensions
modern formats where supported
responsive `srcset`/`sizes`
lazy loading below the fold
explicit aspect ratio
poster/still fallback
```

For long-running visual loops, assess whether a video asset is more
appropriate than a heavy animated image.

Vercel recommends video over animated GIF for looping animation in many
cases and emphasizes still fallbacks and reduced-motion handling.
[Vercel Web Interface Guidelines](https://vercel.com/design/guidelines)

# 55. Motion system: from intent to implementation

Use this implementation worksheet before adding any non-trivial
animation:

``` text
MOTION NAME:
PURPOSE:
TRIGGER:
SOURCE / ANCHOR:
TARGET:
PROPERTY:
DURATION:
EASING:
DELAY:
STAGGER:
INTERRUPTION:
REDUCED-MOTION ALTERNATIVE:
PERFORMANCE RISK:
TEST METHOD:
```

## 55.1 Motion hierarchy

Not every element needs motion.

A useful hierarchy is:

``` text
Tier 0 — static
Most content

Tier 1 — state feedback
Buttons, fields, toggles

Tier 2 — contextual transition
Menus, dialogs, drawers, navigation

Tier 3 — brand expression
Logo, hero art, editorial moments

Tier 4 — immersive motion
Only when the product itself depends on it
```

The higher the tier, the stronger the justification required.

## 55.2 One focal event at a time

When several elements animate together:

``` text
choose one focal motion
→ make supporting motions quieter
→ avoid competing trajectories
→ keep the sequence understandable
```

Atlassian's current motion guidance explicitly recommends a single clear
focal point when multiple elements animate. [Atlassian Design ---
Motion](https://atlassian.design/foundations/motion)

## 55.3 Use timing as hierarchy

Shorter:

``` text
hover
press
small feedback
```

Longer:

``` text
larger spatial transitions
brand moments
slow ambient motion
```

Do not create a slow animation merely because it is visually pleasing in
isolation.

Material's motion guidance describes dynamic duration based on travel
distance and surface change instead of one fixed duration for all
animation. [Material Design --- Duration &
easing](https://m1.material.io/motion/duration-easing.html)

# 57. Visual QA protocol: the final 10%

The last pass should be treated as professional visual editing.

## Pass A --- zoomed-out hierarchy

View the whole page.

Ask:

``` text
What is the first focal point?
Where does attention go next?
Are sections visually distinct?
Are any areas fighting for attention?
```

## Pass B --- normal reading distance

Inspect as a real user would.

Check:

-   heading wraps
-   body rhythm
-   control clarity
-   image/text relationship
-   spacing consistency
-   visual weight

## Pass C --- zoomed inspection

Inspect at high zoom.

Look for:

-   1--2px misalignments
-   inconsistent border tones
-   uneven padding
-   icon optical mismatch
-   awkward radius junctions
-   text baselines
-   image crop errors
-   animation seams

## Pass D --- subtraction pass

Temporarily remove:

``` text
decorations
badges
rules
dots
icons
shadows
gradients
motion
```

Then reintroduce only what materially improves the page.

## Pass E --- content stress test

Replace ideal copy with:

``` text
very short
normal
very long
localized/expanded
```

Confirm the hierarchy remains intact.

-   Never place secrets, private tokens, or privileged credentials in
    client-side code.
-   Treat all user-controlled input as untrusted.
-   Prefer framework and platform security primitives over custom
    security mechanisms.
-   Do not disable security protections merely to simplify development.
-   Keep authorization decisions server-side when the client cannot be
    trusted.
-   Review dependencies before introducing them; minimize supply-chain
    surface area.
-   Treat third-party scripts as security and privacy dependencies, not
    harmless snippets.
-   Document security-relevant assumptions and known limitations.

### Security decision loop

``` text
ASSET / DATA
→ TRUST BOUNDARY
→ THREAT
→ CONTROL
→ IMPLEMENTATION
→ TEST
→ EVIDENCE
```

Security is a release gate, not a post-launch cleanup task.

## 63.2 Privacy and data minimization

Design only the data collection, storage, transmission, and retention
required for the user and product outcome.

Check:

``` text
data collected
purpose
consent / legal basis where applicable
retention
sharing / third parties
sensitive fields
user visibility
user control
logging exposure
analytics exposure
```

Do not collect data merely because it might be useful later.

For analytics and personalization, prefer the minimum data needed to
answer the product question.

## 63.3 Internationalization and localization

Internationalization is an architectural requirement when the product
may support multiple locales.

Design for:

``` text
language
script
text expansion
text contraction
pluralization
number formatting
currency
units
dates / times / time zones
RTL / LTR
locale-specific sorting
accessible translated labels
font / glyph coverage
localized media
```

Test actual translated strings rather than replacing text with arbitrary
longer English copy.

Do not encode language-specific assumptions into layout, component
logic, or date/number formatting.

For Indic, Arabic, CJK, and other scripts, verify shaping, fallback
fonts, line height, wrapping, numerals, and punctuation with real
content.

## 63.4 Localization stress protocol

Every layout that is intended to localize should survive:

``` text
base locale
+30% expansion
long-label locale
RTL locale where applicable
multiline labels
localized dates
localized currency
localized error messages
```

Any component that breaks under legitimate localization pressure must be
redesigned rather than patched with arbitrary clipping.

# 75. Deep browser-facing frontend craft layer --- HTML, CSS, JavaScript

This layer upgrades the skill from "design a high-quality frontend" to
"reason like a meticulous browser engineer, designer, and creative
director at the same time."

The agent must use the browser platform as a first-class design
material. HTML should carry meaning and useful behavior; CSS should own
visual presentation, layout, responsive adaptation, and state whenever
practical; JavaScript should add orchestration, behavior, data flow, and
enhancement rather than replacing capabilities the platform already
provides.

## 75.1 Browser-first operating model

Use this decision hierarchy before writing frontend code:

``` text
SEMANTIC HTML
→ native browser capability
→ CSS state/layout/presentation
→ JavaScript orchestration
→ framework abstraction
→ third-party library
```

Do not jump directly to a framework component or JavaScript
implementation if HTML or CSS already solves the requirement more
robustly.

The agent should continuously ask:

``` text
What can the browser do for free?
What must be represented semantically?
What must adapt through CSS alone?
What genuinely requires JavaScript?
What can remain usable before JavaScript loads?
What can fail safely?
What should remain fast on a low-end phone?
```

This is not "minimal JavaScript" as an aesthetic preference. It is a
complexity-control strategy: native behavior reduces code, interaction
bugs, accessibility debt, and maintenance cost.

## 75.2 HTML engineering: meaning before appearance

HTML is the information architecture encoded for browsers, assistive
technologies, search engines, and other consumers.

### Core rules

``` text
Use the most specific semantic element that matches the user-facing role.
Prefer <a> for navigation.
Prefer <button> for actions.
Prefer <label> with controls.
Prefer real headings for hierarchy.
Prefer lists for list structures.
Prefer <table> for tabular data.
Prefer <dialog> for modal dialogs when behavior fits.
Prefer <details>/<summary> for native disclosure when behavior fits.
Use landmarks intentionally.
Use ARIA to complete semantics, not replace native semantics.
```

Semantic HTML provides native interaction and accessibility behaviors
that would otherwise need to be recreated in JavaScript. MDN explicitly
recommends semantic elements such as `<button>` instead of generic
containers because native controls bring keyboard behavior and other
built-in capabilities. [MDN --- HTML and
accessibility](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/HTML)

### Landmark architecture

A normal document should be structurally understandable without CSS:

``` text
body
├── skip link
├── header
│   └── nav
├── main
│   ├── section / article / supporting regions
│   └── section / article / supporting regions
└── footer
```

Use repeated landmarks only when the repetition is meaningful. Do not
create a forest of empty `<section>` elements merely for styling hooks.

### Headings

The heading hierarchy should express the content structure, not the
desired font size.

``` text
<h1> page/topic
  <h2> major section
    <h3> subsection
```

Use CSS to style hierarchy after semantic hierarchy is correct.

### Links versus buttons

``` text
A link changes location, resource, or URL state.
A button performs an action.
```

Do not style a link as a fake button and then add JavaScript because the
visual design demanded it. Use the correct primitive first, then style
it to fit the system.

### Forms

Every form control should have:

``` text
visible or programmatic label
name
appropriate input type
autocomplete semantics where relevant
validation strategy
help/error relationship
keyboard path
success/recovery state
```

Use native constraints where they genuinely help (`required`, `min`,
`max`, `pattern`, `type`, `autocomplete`) and augment them with
application validation where needed. Do not duplicate native behavior
without a reason.

### Accessible names

Before adding `aria-label`, ask whether visible text, `<label>`,
`<legend>`, `<caption>`, or associated content already provides the
accessible name. Redundant ARIA can make the accessibility tree harder
to reason about.

### Media HTML

For meaningful media:

``` text
alt text
intrinsic dimensions
responsive source strategy
loading priority
captions/transcripts when needed
poster/fallback for video
reduced-motion strategy for animated media
```

Do not let images establish unknown layout dimensions after paint.
Reserve their space.

### Responsive images

Use HTML image capabilities when content is art-directed or
density-sensitive:

``` text
<picture>
  <source media="..." srcset="...">
  <img src="..." width="..." height="..." alt="...">
</picture>
```

Use `srcset`/`sizes` when the same asset should adapt to viewport
density/size. The agent should choose the simplest source strategy that
actually matches the design and content model.

### Native interactive HTML

Prefer platform elements before custom widgets:

``` text
button
input
select
textarea
details / summary
dialog
progress
meter
output
```

A custom control should be treated as a higher-complexity choice with
explicit accessibility and keyboard behavior requirements.

## 75.3 HTML performance architecture

The agent must understand that HTML participates in the critical
rendering path.

Optimize for:

``` text
small DOM depth
low unnecessary node count
correct source order
early critical content
stable dimensions for media
minimal third-party markup
progressive enhancement
```

Do not generate an entire visual system as deeply nested wrappers merely
because the design tool or framework permits it.

MDN notes that DOM size, markup order, and resource inclusion choices
can materially affect rendering performance. [MDN --- HTML performance
optimization](https://developer.mozilla.org/en-US/docs/Web/Performance/HTML)

## 75.4 CSS engineering: think in layout, paint, and composition

CSS decisions should be grouped into three questions:

``` text
LAYOUT
Where and how big is it?

PAINT
How does it look?

COMPOSITING
How does it interact with other painted layers?
```

Examples:

``` text
layout: grid, flexbox, width, height, gap, padding, margin, position
paint: color, background, border, border-radius, shadow, gradients, text
compositing: opacity, transform, filter, backdrop-filter, blend modes, masks
```

When debugging a visual issue, identify which layer owns the problem
before adding another declaration.

### CSS architecture

Prefer:

``` text
@layer / architecture boundary
→ tokens
→ reset/base
→ layout primitives
→ components
→ state styles
→ responsive rules
→ page composition
→ utilities only where they reduce repetition
```

Use custom properties for repeated system decisions:

``` css
:root {
  --space-1: 0.25rem;
  --space-2: 0.5rem;
  --radius-sm: 0.625rem;
  --radius-md: 1rem;
  --duration-fast: 160ms;
  --ease-standard: cubic-bezier(.2, .8, .2, 1);
}
```

Avoid "magic-number drift": five slightly different radii or seven
unrelated gaps are often evidence that the system has not been decided.

### The cascade is part of architecture

Prefer a small, understandable cascade. When a component needs a late
override to survive many earlier selectors, repair the architecture
instead of stacking specificity.

Use:

``` text
low specificity
layer boundaries
component-local rules
state selectors
logical responsive overrides
```

Be deliberate with `!important`; it should be a documented exception,
not a normal conflict-resolution mechanism.

## 75.5 Modern layout mechanics

Use the browser's intrinsic sizing model aggressively.

Preferred tools:

``` text
Grid for two-dimensional page systems.
Flexbox for one-dimensional distribution.
Container queries for component-level adaptation.
max-width / minmax() for content-driven sizing.
clamp() for fluid values with explicit bounds.
aspect-ratio for media boxes.
min(), max(), calc(), fit-content() for constraint composition.
logical properties for direction-aware layouts.
```

Prefer CSS to measuring layout in JavaScript. Vercel's current interface
guidance explicitly recommends letting flex/grid/intrinsic sizing
perform layout instead of measuring and positioning with JavaScript.
[Vercel Web Interface Guidelines](https://vercel.com/design/guidelines)

### Container-first responsiveness

When a component changes because of the space available to that
component rather than the device itself, prefer container queries over
global viewport breakpoints.

Think:

``` text
component width
→ component layout mode
```

instead of:

``` text
phone/tablet/desktop
→ guessed component behavior
```

Viewport media queries remain appropriate for page-level composition,
navigation, and global density changes.

## 75.6 CSS responsive composition

Responsive design should not be "desktop, then shrink."

For every major section define:

``` text
wide composition
comfortable composition
compact composition
```

Then decide independently:

``` text
columns
content order
alignment
spacing
type scale
image crop
controls
navigation
visibility
interaction density
```

A two-column desktop hero may become stacked; a large navigation may
become a disclosure; an image may move below its copy; metadata may
become secondary; decorative layers may disappear.

Do not preserve desktop composition merely because it technically fits
at a smaller width.

## 75.7 Fluid typography

Typography should often scale continuously rather than jump between a
few arbitrary breakpoints.

Use bounded formulas such as:

``` css
font-size: clamp(2.25rem, 6vw, 5.5rem);
```

`clamp()` provides a minimum, preferred, and maximum bound and is widely
available. [MDN ---
clamp()](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/clamp)

Use fluid type when it improves the relationship between viewport,
hierarchy, and line length. Do not use fluidity for every label merely
because the syntax is available.

## 75.8 Typography engineering --- the full system

Typography is not "choose a nice font." It is the controlled
relationship among:

``` text
family
weight
width
optical size
size
line height
tracking
measure
case
numerals
language
contrast
rendering
loading
fallbacks
```

### Typographic role system

Define roles before choosing values:

``` text
DISPLAY
HERO
H1 / H2 / H3
BODY
BODY SMALL
UI
LABEL
CAPTION
DATA / NUMERIC
CODE
```

Then define:

``` text
family
weight range
size
line-height
letter-spacing
max measure
```

### Type scale

Prefer a coherent progression rather than isolated sizes.

A practical system might derive from a ratio, a fluid curve, or design
tokens. The exact ratio is not sacred. Consistency and content fit
matter more than mathematical purity.

### Line height

Large display text often needs a tighter line-height than body text, but
line-height must be judged by actual glyphs and line count.

Do not force a single global value such as `1.5` onto every role.

### Measure

Long text is a composition problem, not merely a font-size problem.

For reading-oriented copy, cap line length so the eye does not need to
traverse an excessively wide measure. Adjust measure before shrinking
type to make a paragraph "fit."

### Tracking

Use letter spacing sparingly:

``` text
large display text → sometimes slightly tighter
body → usually near normal
all-caps UI → often slightly expanded
small text → do not over-tighten
```

Do not use letter spacing as a repair for the wrong font choice.

### Optical sizing and variable fonts

When the chosen variable font supports it, use:

``` css
font-optical-sizing: auto;
```

or intentionally control registered/custom axes when there is a real
typographic reason.

The `opsz` axis can alter glyph construction for different reading
sizes; `wght` and `wdth` can alter weight and width. [MDN ---
font-optical-sizing](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/font-optical-sizing)
[MDN ---
font-variation-settings](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/font-variation-settings)

### Text wrapping

For headings, test:

``` css
text-wrap: balance;
```

when a balanced multi-line heading materially improves hierarchy.

For body copy or situations where line quality matters more than raw
speed, `text-wrap: pretty` can be considered. Both are browser-level
wrapping strategies, not excuses to insert manual `<br>` tags
everywhere. [MDN ---
text-wrap-style](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-wrap-style)

Use `<br>` intentionally only when a line break is part of the authored
composition and should remain semantically/visually stable.

### Heading composition algorithm

For every prominent heading:

``` text
choose family
→ choose weight
→ choose size
→ choose measure
→ choose line-height
→ inspect wrap at target widths
→ decide balance/pretty/normal
→ tune tracking
→ inspect optical alignment
```

Do not optimize headline typography solely from a desktop screenshot.

### Numerals

For metrics, prices, statistics, and comparisons, consider:

``` css
font-variant-numeric: tabular-nums;
```

When the goal is tabular alignment, use tabular numerals. When the goal
is editorial elegance, proportional numerals may be better.

### Text rendering

Avoid transforming text nodes merely for decorative animation. Animate a
containing wrapper where possible to reduce text rasterization
surprises.

Avoid overly thin text, aggressive opacity, low-contrast gray, and
effects that blur glyph edges.

### Font loading

Treat font loading as part of layout stability:

``` text
choose minimal families
subset real scripts
load only needed weights
use variable fonts when justified
preload only critical fonts
provide a deliberate fallback
measure the fallback transition
```

The goal is not "zero fallback ever." The goal is to make the transition
predictable, legible, and low-impact.

## 75.9 Gradient engineering --- teach the AI to create depth without noise

Gradients are a material, not decoration.

Use them for:

``` text
focal emphasis
light direction
spatial separation
atmosphere
depth
brand energy
state indication
surface hierarchy
image/text legibility
```

### Gradient types

``` text
linear-gradient → directional light, bands, edge fades
radial-gradient → spotlight, glow, soft focal field
conic-gradient → circular progress, spectral rotation, controlled color wheel
multiple gradients → layered lighting / atmosphere
gradient + mask → controlled fade / reveal
gradient + blend mode → compositional integration
```

MDN documents linear, radial, and conic gradient functions as
first-class CSS image primitives; conic gradients place color stops
around an angular path rather than along a line. [MDN --- Using CSS
gradients](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Images/Using_gradients)
[MDN ---
conic-gradient()](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/gradient/conic-gradient)

### Gradient rules

``` text
1. Establish the visual job.
2. Pick the light direction or focal area.
3. Choose the minimum number of stops.
4. Use the color space intentionally.
5. Preserve text contrast.
6. Inspect banding and edge behavior.
7. Test the gradient on real content, not an empty artboard.
8. Remove it if a flat surface communicates better.
```

Do not automatically add a multi-color gradient to a hero because
"premium sites use gradients."

### Modern color spaces

Use perceptual color spaces when they simplify a color system or create
more coherent interpolation:

``` css
color-mix(in oklab, var(--brand) 70%, white)
oklch(70% 0.16 260)
```

`color-mix()` supports interpolation in multiple color spaces, and MDN
notes that Oklab is useful for perceptually uniform gradients while
Oklch can help preserve chroma during interpolation. [MDN ---
color-mix()](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/color_value/color-mix)
[MDN ---
oklch()](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/color_value/oklch)

Use modern color spaces because they solve a visual problem, not because
the syntax looks advanced.

### Gradient failure modes

Reject or revise gradients that cause:

``` text
text contrast loss
visual vibration
muddy neutral transitions
banding
unexplained color noise
false affordance
overly strong focal competition
large GPU/paint cost without benefit
```

## 75.10 Morphism and material systems --- use the right one, not every one

"Morphism" is not a design goal by itself. It is a family of ways to
communicate surface, depth, softness, translucency, tactility, or
atmosphere.

The agent must choose a material system based on:

``` text
product character
interaction hierarchy
content density
background variability
contrast requirements
motion context
device capability
brand language
```

### Material taxonomy

  ---------------------------------------------------------------------------------------
  Material style     What it        Good use         Avoid when
                     communicates                    
  ------------------ -------------- ---------------- ------------------------------------
  **Glassmorphism /  depth,         navigation,      text sits over busy moving imagery;
  translucent        layering,      overlays,        content layer becomes muddy
  glass**            floating UI    contextual       
                                    controls         

  **Liquid /         dynamic        hero-adjacent    used on every card or ordinary
  refractive         layered depth  controls,        content blocks
  translucent                       premium          
  material**                        navigation,

Apple's current materials guidance frames materials as tools for depth
and hierarchy, emphasizes keeping functional translucent material
visually distinct from content, and warns against using material as an
arbitrary color effect. [Apple ---
Materials](https://developer.apple.com/design/human-interface-guidelines/materials)

### Glass implementation model

A strong web glass surface usually combines:

``` css
background: color-mix(in oklab, white 10%, transparent);
backdrop-filter: blur(18px) saturate(140%);
border: 1px solid color-mix(in oklab, white 22%, transparent);
box-shadow:
  0 10px 30px rgba(0,0,0,.08),
  0 1px 0 rgba(255,255,255,.20) inset;
```

The exact values are not universal. The important model is:

``` text
semi-transparent surface
+ controlled blur
+ edge definition
+ restrained elevation
+ strong content contrast
```

`backdrop-filter` affects content behind the element and requires
transparency or partial transparency for the underlying material to be
visible. It is broadly supported in modern browsers but should still be
tested against the target browser matrix. [MDN ---
backdrop-filter](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/backdrop-filter)

### Glass failure audit

Reject the glass treatment when:

``` text
text loses contrast
background detail becomes distracting
blur cost is excessive
multiple translucent layers stack into gray mud
controls become visually indistinguishable from content
the material appears everywhere
```

### Depth discipline

Depth should communicate:

``` text
what is above what
what is interactive
what is temporary
what is primary
what recedes
```

Do not give ordinary body text "floating" shadows or heavy depth.
Apple's spatial-layout guidance specifically warns that excessive depth,
especially around text, can reduce legibility and create visual
discomfort. [Apple --- Spatial
layout](https://developer.apple.com/design/human-interface-guidelines/spatial-layout/)

## 75.11 Shadows, borders, and elevation

Treat shadow as a lighting model, not a blur value.

A refined shadow may use multiple layers:

``` text
ambient broad shadow
+
contact shadow
+
optional subtle inset/highlight
```

Use stronger contrast for interactive elevation changes and lower
contrast for passive surfaces.

Borders can add crispness where blur/shadow becomes muddy. Use a
coherent border alpha and hue family rather than arbitrary grays on
every component.

Nested radii should be intentionally related. A child should not
visually bulge beyond the curvature logic of its parent unless the
overlap is deliberate.

## 75.12 Compositing, blend modes, and masks

Modern CSS composition can produce sophisticated art direction without
canvas or image editing when used selectively.

Useful primitives include:

``` text
mix-blend-mode
background-blend-mode
filter
backdrop-filter
mask-image
clip-path
opacity
transform
```

`mix-blend-mode` controls how an element's content blends with what is
behind it inside its stacking context. [MDN ---
mix-blend-mode](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/mix-blend-mode)

Use blend modes for:

``` text
controlled image overlays
brand color interaction
poster-style composition
texture integration
atmospheric effects
```

Do not use blend modes for ordinary text if the result can reduce
contrast or become background-dependent.

## 75.13 JavaScript engineering for frontend interaction

JavaScript should own behavior that genuinely requires state,
coordination, asynchronous work, or browser APIs.

### JavaScript decision hierarchy

``` text
native HTML behavior
→ CSS selector/state
→ CSS animation/transition
→ small local JS controller
→ shared utility
→ framework state
→ external library
```

The agent should justify every jump downward in this hierarchy.

### State ownership

Prefer the smallest state scope that is correct:

``` text
DOM state for native controls
local component state for local UI
URL state for shareable/navigation state
server state for remote data
shared client state only for genuinely shared interactions
persistent storage only when persistence is a product requirement
```

Do not put modal-open state, tooltip-open state, or one form's temporary
state in a global store without a reason.

## 75.14 JavaScript event architecture

Prefer event delegation where many similar dynamic children would
otherwise receive duplicate listeners.

Do not attach listeners repeatedly after every render if the DOM can
support a stable delegated listener.

Use:

``` js
button.addEventListener('click', onClick);
```

with an owned lifecycle. When the component or controller is destroyed,
clean up what it created.

Where supported, use `AbortController` to group listener or fetch
cleanup so lifecycle boundaries remain explicit.

### Interaction state machine

For meaningful interactions, model states before coding:

``` text
idle
→ hover / focus
→ pressed
→ pending
→ success
→ error
→ retry / recover
```

Not every component needs every state. The point is to eliminate
accidental "half-states."

## 75.15 Async JavaScript and race conditions

Treat asynchronous UI as a concurrency problem, not only a syntax
problem.

Promises are foundational to modern async JavaScript, and
`async`/`await` provides a readable way to express asynchronous control
flow. [MDN ---
promises](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Using_promises)

For every async action, ask:

``` text
What happens if the user clicks twice?
What happens if the request returns out of order?
What happens if the component disappears?
What happens if the network is offline?
What happens if the response is stale?
What happens if the action is retried?
```

Use cancellation where appropriate. For fetch-driven interfaces,
associate requests with an `AbortController` when stale work can become
irrelevant.

Never let stale asynchronous responses overwrite newer user intent.

## 75.16 DOM reads and writes

Avoid layout thrashing.

Bad pattern:

``` text
read layout
write style
read layout
write style
read layout
```

Better:

``` text
batch reads
→ compute
→ batch writes
```

Prefer CSS layout rules over JS-measured positioning. Vercel explicitly
recommends letting the browser size things using flex/grid/intrinsic
layout and avoiding layout thrash. [Vercel Web Interface
Guidelines](https://vercel.com/design/guidelines)

## 75.17 Observers: use the browser to notice change

Prefer observer APIs when the requirement is about the environment
rather than constant polling:

``` text
IntersectionObserver → viewport/visibility relationship
ResizeObserver → element size changes
MutationObserver → DOM subtree mutations
PerformanceObserver → performance entries
```

Do not implement scroll/resize polling loops when an observer provides a
more direct signal.

## 75.18 Animation architecture: CSS first, JS when coordination requires it

Use CSS transitions/animations for simple state interpolation:

``` text
hover
focus
open/closed
visibility
small transforms
opacity
```

Use JavaScript animation when you genuinely need:

``` text
scroll-linked coordination
physics/custom timelines
complex sequential choreography
external data synchronization
imperative browser animation control
```

MDN recommends CSS animation for many essential DOM animations because
browser-managed CSS animation can be more efficient than
JavaScript-driven style manipulation, while acknowledging that both
approaches have valid use cases. [MDN --- CSS and JavaScript animation
performance](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/CSS_JavaScript_animation_performance)

Avoid:

``` css
transition: all;
```

Explicitly list the properties being animated. Vercel's current guidance
similarly recommends avoiding `transition: all` and generally animating
efficient properties such as `opacity` and `transform`. [Vercel Web
Interface Guidelines](https://vercel.com/design/guidelines)

## 75.19 View Transitions

When navigation or state changes would benefit from maintaining visual
continuity, consider the View Transition API.

The API can animate transitions between states in a single-page app and
can also support transitions between documents. MDN describes the API as
a way to reduce cognitive load and perceived loading latency by
preserving continuity between views. [MDN --- View Transition
API](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API)

Rules:

``` text
progressive enhancement
→ skip when unsupported or inappropriate
→ preserve focus and reading position
→ never block essential navigation on decorative animation
→ use named transitions only for meaningful continuity
```

Do not apply a page-wide cinematic transition to every navigation just
because the API exists.

## 75.20 JavaScript performance model

Remember the browser has finite main-thread time.

Expensive work includes:

``` text
large JS bundles
synchronous parsing/execution
heavy data transforms
large DOM mutations
layout reads/writes
canvas-heavy work
frequent animation callbacks
large JSON processing
third-party scripts
```

Keep interaction handlers cheap. If work is CPU-heavy and independent of
immediate layout, consider an appropriate worker architecture.

MDN notes that CPU-heavy JavaScript can block the main thread and
degrade interaction, rendering, download performance, and battery life.
[MDN --- JavaScript
performance](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Performance/JavaScript)

## 75.21 HTML/CSS/JS cooperation contract

The agent should distribute responsibility like this:

``` text
HTML
  meaning
  structure
  native behavior
  accessible relationships
  content

CSS
  layout
  responsive composition
  visual hierarchy
  surfaces
  typography
  animation between visual states
  media adaptation

JavaScript
  behavior
  orchestration
  data fetching
  complex state
  browser APIs
  asynchronous workflows
  progressive enhancement
```

When a responsibility could belong to two layers, prefer the layer with
the smallest state and maintenance burden.

### HTML anti-patterns

``` text

button with no accessible name
links that do not navigate
heading tags chosen only by visual size
missing labels
fake tables made from divs

```

### CSS anti-patterns

``` text

magic-number proliferation
unbounded z-index escalation
fixed heights for dynamic content

```

# 76. Premium website pattern analysis --- learn from Apple and other high-craft systems

Reference websites should be treated as design evidence, not
paint-by-numbers templates.

Apple's current public guidance is especially useful as a **principle
library**: purpose, agency, responsibility, familiarity, flexibility,
simplicity, craft, and delight. Apple explicitly describes simplicity as
clarity and friction reduction rather than emptiness, and craft as
careful execution across typography, color, animation, performance, and
iteration. [Apple --- Design
principles](https://developer.apple.com/design/human-interface-guidelines/design-principles)
[Apple --- Principles of great design,
WWDC26](https://developer.apple.com/videos/play/wwdc2026/250/)

## 76.1 What to learn from Apple's product storytelling

Current Apple product pages commonly use a long-form story architecture
in which each section has one dominant message, a large visual focal
point, supporting explanation, and a controlled transition to the next
idea. The Apple Vision Pro page is a current example with focused
sections for productivity, photos/video, connection, apps, platform,
technology, and values. [Apple Vision
Pro](https://www.apple.com/apple-vision-pro/)

Extract the architecture:

``` text
ONE IDEA
→ ONE FOCAL VISUAL
→ MINIMAL SUPPORTING COPY
→ ONE RELEVANT ACTION OR NEXT STEP
→ TRANSITION
→ NEXT IDEA
```

Do not copy Apple-specific products, copy, or composition literally.

## 76.2 Premium-site pattern library

Teach the AI to recognize these recurring high-craft patterns:

``` text
Editorial hero
Product hero
Immersive visual section
Split narrative section
Proof / specification section
Interactive showcase
Feature grid
Comparison section
Focused CTA
Footer ecosystem
```

For each pattern define:

``` text
purpose
content density
visual focal point
copy measure
interaction intensity
responsive transformation
likely material system
performance risk
accessibility risk
```

## 76.3 Visual hierarchy algorithm

For each viewport, identify:

``` text
1 primary focal point
1 primary action
1 supporting hierarchy
secondary information
background atmosphere
```

If everything is visually loud, nothing is primary.

Use contrast through a combination of:

``` text
scale
weight
space
alignment
color
position
surface
motion
```

Do not use all of them at maximum intensity simultaneously.

## 76.4 Visual density modes

The agent should deliberately choose one density mode per section:

``` text
AIRY
minimal text, large media, strong pauses

BALANCED
normal marketing/product composition

DENSE
data, settings, comparison, enterprise tasks

IMMERSIVE
large media, depth, motion, atmosphere
```

A page may mix modes, but each transition must feel intentional.

## 76.5 "Apple-like" does not mean "make everything white, huge, and sparse"

Do not imitate surface attributes without understanding their purpose.

Instead extract:

``` text
clarity
hierarchy
restraint
craft
coherence
purposeful motion
content-focused composition
```

The agent may then translate those principles into editorial, dark,
colorful, playful, technical, brutalist, luxury, or other visual
directions when the project needs it.

After the first render, do not ask only "Does it look good?"

Ask:

``` text

For every visual defect, classify it:

``` text

# 85. Agentic asset, image, icon, and motion mastery layer

This section teaches the agent to behave more like a senior frontend
designer- developer operating a real product system than like a model
assembling a visually plausible first draft.

The agent must treat **content assets, imagery, icons, typography, and
motion as first-class implementation decisions**. These are not
decoration added after layout.

The operating loop becomes:

``` text
INTENT
→ REFERENCE DISCOVERY
→ CONTENT / ASSET MODEL
→ SEMANTIC HTML
→ CSS COMPOSITION
→ ICONOGRAPHY
→ IMAGERY / ART DIRECTION
→ MOTION MODEL
→ IMPLEMENTATION
→ RENDER
→ INSPECT
→ MEASURE
→ DIAGNOSE
→ CHANGE ONE HYPOTHESIS
→ RE-RENDER
→ RE-CHECK
→ REMOVE NOISE
→ RELEASE EVIDENCE
```

The agent must not stop because the page "looks good" in a first render.

## 85.1 Asset-first reasoning

Before inserting an image, icon, animation, video, or generated graphic,
classify its role:

``` text
IDENTITY       brand/product/people/location identity
PRODUCT        object/product/interface being explained
EDITORIAL      story-supporting photography or illustration
EXPLANATORY    diagram, process, comparison, evidence
PROOF          screenshot, result, before/after, case-study evidence
NAVIGATION     symbol that helps recognition or orientation
ACTION         icon that explains an interactive control
STATUS         success/warning/error/loading state symbol
ATMOSPHERE     non-essential visual mood or depth
TEXTURE        low-information visual surface treatment
DECORATIVE     visual element with no semantic payload
```

Then select the lightest medium that communicates the role correctly:

``` text
plain text
→ semantic HTML
→ CSS shape
→ SVG icon
→ inline SVG illustration
→ raster image
→ responsive image set
→ short video
→ Lottie/dotLottie
→ WebGL / 3D
```

Do not jump to a raster image when CSS or SVG communicates the idea more
sharply. Do not jump to WebGL when a normal image or CSS composition is
sufficient. Do not use a generic stock image to fill a gap merely
because the layout has empty space.

## 85.2 Asset selection decision contract

For every non-trivial visual asset, define internally:

``` text
ROLE:
MESSAGE:
USER VALUE:
SOURCE:
AUTHORITY / LICENSE:
SEMANTIC STATUS:
FORMAT:
ASPECT RATIO:
FOCAL POINT:
MOBILE CROP:
LOADING PRIORITY:
FALLBACK:
ACCESSIBILITY:
MOTION BEHAVIOR:
PERFORMANCE COST:
RESPONSIVE RULE:
REMOVAL TEST:
```

If several assets satisfy the same purpose, prefer the one with the best
total system fit rather than the most visually dramatic isolated
appearance.

## 85.3 Real-site reference study protocol

When the user asks for a site "like Apple," "like Stripe," "like
Linear," or similar, the agent should use the live public site as a
**reference system**, not as a source to clone.

Inspect the actual URL when web access is available. Record:

``` text
URL
CAPTURE DATE
VIEWPORT
PAGE TYPE
NAVIGATION MODEL
TYPOGRAPHIC SCALE
IMAGE SCALE
IMAGE ROLE
SECTION RHYTHM
CTA HIERARCHY
ICON STYLE
MOTION STYLE
MATERIAL / SURFACE SYSTEM
RESPONSIVE TRANSFORMATION
PERFORMANCE OBSERVATIONS
ACCESSIBILITY OBSERVATIONS
BRAND-SPECIFIC ELEMENTS TO AVOID COPYING
TRANSFERABLE PRINCIPLES
```

Useful public reference set:

``` text
Apple        https://www.apple.com/
Apple Design https://developer.apple.com/design/
Vercel       https://vercel.com/

## 85.4 Live-reference refresh rule

The agent must re-check reference URLs when the requested output depends

# 86. Supersemantic image engineering

Images are part of information architecture. The agent must decide **why
the image exists before deciding how it is styled**.

## 86.1 Image role → implementation mapping

  ---------------------------------------------------------------------
  Image role                         Preferred implementation
  ---------------------------------- ----------------------------------
  Content-bearing photo              `<img>` with meaningful `alt`

  Art-directed responsive photo      `<picture>` + source variants

  Decorative background              CSS background or decorative
                                     `<img alt="">` depending semantics

  Diagram/illustration               SVG when practical

  Infographic with meaningful text   HTML/SVG, not a flattened image
                                     when possible

  Product image                      `<img>` with real dimensions,
                                     focal point, useful alt

  Hero visual                        Responsive image/video with
                                     reserved geometry

  Screenshot                         `<figure>` + `<figcaption>` when
                                     explanatory

  Portrait                           Meaningful alt describing
                                     identity/context when needed

  Texture/grain                      Decorative, inaccessible to
                                     assistive tech

  Logo/wordmark                      SVG or optimized image with
                                     brand-appropriate accessible name

  Animated illustration              Video/Lottie/SVG/HTML depending
                                     complexity and need
  ---------------------------------------------------------------------

    ## 86.2 The semantic image test

    Ask:

    ```text
    Does the user need the information contained in this visual?
    Does the visual identify the subject?
    Does the visual prove a claim?
    Does the visual explain a process?
    Does the visual simply establish atmosphere?
    Would removing it reduce understanding?

Then choose semantics accordingly.

### Meaningful image

Use a meaningful alternative text strategy. Describe the useful meaning,
not every visible pixel.

### Decorative image

Use an empty `alt` or an equivalent decorative treatment so assistive
technology does not receive redundant information.

### Functional image

The accessible name must describe the action or destination, not merely
say "image."

### Text-bearing image

Do not hide essential text inside a raster image when HTML text would be
more accessible, responsive, searchable, localizable, and maintainable.

## 86.3 Prefer `<figure>` when the relationship matters

Use:

``` html
<figure>
  <img
    src="..."
    alt="..."
    width="1600"
    height="1000"
  >
  <figcaption>...</figcaption>
</figure>
```

when the image and caption form one explanatory unit.

Do not wrap every decorative image in a figure merely because the
element exists.

## 86.4 Responsive images are a semantic performance decision

The agent should know the difference between:

``` text
same image, different display sizes
vs
same subject, different crops / compositions
```

Use `srcset` + `sizes` for density/size selection.

Use `<picture>` when art direction requires different source files or
crops.

Example:

``` html
<picture>
  <source
    media="(max-width: 47rem)"
    srcset="hero-mobile.avif 1x, hero-mobile@2x.avif 2x"
  >
  <source
    media="(min-width: 48rem)"
    srcset="hero-wide.avif 1x, hero-wide@2x.avif 2x"
  >
  <img
    src="hero-wide.jpg"
    alt="Descriptive subject"
    width="2400"
    height="1350"
    decoding="async"
  >
</picture>
```

The media query should represent an actual composition change, not be
added because responsive markup "looks professional."

## 86.5 Image geometry must be known before paint

Every major image should reserve space through real intrinsic
dimensions, `aspect-ratio`, or equivalent geometry.

Avoid:

``` text
image loads
→ container changes height
→ text shifts
→ user loses reading position
```

The image should have a known box before the final asset arrives.

## 86.6 `loading`, `decoding`, and `fetchpriority` are decisions

Use them deliberately.

Typical reasoning:

``` text
above-the-fold LCP candidate
→ carefully consider high priority

ordinary below-the-fold image
→ lazy loading is often appropriate

non-critical image
→ async decode where suitable
```

Do not add `loading="lazy"` to every image. Do not add
`fetchpriority="high"` to every image. Do not preload every image.

The agent must identify the actual LCP candidate and measure before
aggressively prioritizing resources.

## 86.7 Image crop and focal point are part of design

Never treat `object-fit: cover` as the end of image art direction.

Define:

``` text
FOCAL POINT
CROP BIAS
MINIMUM SUBJECT VISIBILITY
MOBILE CROP
TABLET CROP
DESKTOP CROP
```

Use `object-position` or art-directed source variants where needed.

For people, products, or faces, ensure the subject remains legible at
the smallest realistic viewport.

## 86.8 Image sourcing hierarchy

Prefer:

``` text
user-provided assets
→ client-approved assets
→ official brand/product assets
→ licensed stock
→ permissively licensed open assets
→ AI-generated asset when appropriate
→ temporary placeholder explicitly labeled
```

Never silently use an asset with unknown licensing as production
content.

Never invent a product screenshot, customer photo, office photo,
certification, review image, or "realistic" business scene and present
it as factual.

## 86.9 Generate instead of fake when the brief needs originality

When a visual must be original, the agent may create an original
illustration, texture, abstract scene, or art direction rather than
inventing a photograph that implies a false real-world event.

Generated visuals should still receive a clear content role:

``` text
ILLUSTRATIVE
ATMOSPHERIC
PRODUCT CONCEPT
DIAGRAM
BRAND ART
```

Do not make illustrative assets masquerade as evidence.

## 86.10 Image anti-patterns

Detect and correct:

``` text
generic smiling business stock photo everywhere
same crop repeated in every section
hero image chosen after layout with no focal-point planning
background image behind dense text without contrast treatment
image with unknown licensing
image with no reserved dimensions
huge PNG used where AVIF/WebP/JPEG/SVG would be better
mobile version created by merely shrinking desktop art
essential text flattened into raster
placeholder photo left in production-like UI
```

## 86.11 Video vs animated image

For looping visual atmosphere, compare:

``` text
CSS animation
→ SVG
→ video
→ Lottie/dotLottie
→ WebGL
```

A short muted looping video can be preferable to an animated GIF for
rich photographic or continuous motion content. Vercel explicitly
recommends video over animated GIF for looping animation and emphasizes
a still fallback and reduced-motion handling. \[Vercel Web Interface
Guidelines\]

Use a video only when the motion adds meaningful value and the cost is
acceptable.

# 87. Professional iconography system

Icons are **interface symbols**, not generic decorative pictures.

## 87.1 Icon decision hierarchy

Use:

``` text
TEXT LABEL
→ NATIVE SYMBOL / PLATFORM SYMBOL
→ ESTABLISHED ICON LIBRARY
→ PROJECT ICON SYSTEM
→ CUSTOM SVG
→ RASTER ICON ONLY AS A SPECIAL ASSET CASE
```

Do not use a random photo, 3D PNG, emoji, or unrelated image as a UI
icon when a recognizable vector symbol exists.

## 87.2 Icon role classification

``` text
ACTION       edit, close, search, share, delete
NAVIGATION   chevron, menu, back, external-link
STATUS       check, warning, error, info
OBJECT       user, folder, document, calendar
SYSTEM       settings, filter, sort, view
BRAND        approved brand mark or custom identity glyph
DECORATIVE   purely visual motif with no semantic meaning
```

## 87.3 Icon family consistency

Within one product surface, establish:

``` text
GRID
VIEWBOX
STROKE OR FILL MODEL
STROKE WIDTH
CORNER LANGUAGE
CAP STYLE
JOIN STYLE
OPTICAL SIZE
DEFAULT COLOR
ACTIVE COLOR
DISABLED COLOR
```

Do not mix a 1.5px rounded-line family with heavy filled symbols without
a specific contextual reason.

## 87.4 Professional icon sources to investigate

Current developer-friendly sources include:

``` text
Lucide
https://lucide.dev/
https://lucide.dev/guide/lucide

Heroicons
https://heroicons.com/

Iconoir
https://iconoir.com/
https://iconoir.com/docs

Phosphor
https://phosphoricons.com/

Apple SF Symbols reference
https://developer.apple.com/sf-symbols/
```

Lucide's current documentation supports vanilla JavaScript, SVG
generation, CSS styling, tree-shaking, and accessibility guidance.
\[Lucide\] Heroicons provides hand-crafted SVG icons and React/Vue
libraries. \[Heroicons\] Iconoir provides SVG, CSS, React, Vue, and
other integrations and documents `currentColor`, icon sizing, stroke
weight, and naming conventions. \[Iconoir\]

## 87.5 Icon search algorithm

When an icon is needed:

``` text
1. Define semantic meaning.
2. Search the established icon family.
3. Search synonyms and object terms.
4. Reject candidates whose metaphor is ambiguous.
5. Check visual weight against neighboring icons.
6. Check optical size at actual usage size.
7. Check filled/outline consistency.
8. Check accessibility role.
9. Check license.
10. Record source.
```

Do not pick an icon because its silhouette merely "looks nice."

## 87.6 Icon ambiguity test

For an unfamiliar visitor, ask:

``` text
Does this symbol have an established interpretation?
Could it mean two opposite things?
Does the label remove ambiguity?
Does its shape remain legible at the smallest size?
```

When ambiguity remains, pair the icon with a visible text label.

## 87.7 Icon-only controls

Icon-only buttons require an accessible name.

Example:

``` html
<button type="button" aria-label="Close dialog">
  <svg aria-hidden="true" viewBox="0 0 24 24">
    <path d="..." />
  </svg>
</button>
```

The visual icon is not the accessible name.

Maintain the hit target even when the visible SVG is small.

## 87.8 Decorative icons

If an icon communicates no additional information:

``` html
<svg aria-hidden="true" focusable="false" ...>
```

Do not feed decorative icons into the accessibility tree.

## 87.9 Inline SVG defaults

For normal interface icons, prefer a controllable vector system such as:

``` svg
<svg
  viewBox="0 0 24 24"
  width="1em"
  height="1em"
  fill="none"
  stroke="currentColor"
  stroke-width="1.75"
  stroke-linecap="round"
  stroke-linejoin="round"
  aria-hidden="true"
>
  ...
</svg>
```

Treat these values as a starting system, not a universal law.

Use `currentColor` when the icon should inherit the semantic
text/control color.

## 87.10 Custom SVG creation protocol

When no existing icon is semantically correct:

``` text
DEFINE CONCEPT
→ choose 24×24 or project grid
→ construct silhouette
→ establish optical center
→ simplify paths
→ align repeated radii
→ establish stroke/fill system
→ test at 12/16/20/24/32px
→ test beside text
→ test on light/dark surfaces
→ test with forced colors/high contrast
→ test accessible name
→ minimize path count
→ validate SVG
→ store source/license metadata
```

Do not trace copyrighted logos or proprietary icons into lookalike
assets.

Custom icons should be original or appropriately licensed.

## 87.11 SVG optimization rules

Before shipping a custom SVG:

``` text
remove editor metadata
remove hidden layers
remove unused defs
remove unnecessary groups
collapse redundant transforms
preserve viewBox
avoid unnecessary embedded raster data
avoid giant path precision where it is not needed
check IDs for collisions when inlining multiple SVGs
```

If the SVG is interactive, also inspect focus and pointer behavior.

## 87.12 Icon animation

Animate icons only when the state change benefits from motion.

Useful:

``` text
menu → close
play → pause
upload → success
loading → complete
expand → collapse
bookmark → saved
```

Prefer:

``` text
stroke/path/transform/opacity change
```

over replacing the icon with an unrelated decorative animation.

For SVG transforms, group moving paths in `<g>` where appropriate and
set a predictable transform box/origin. Vercel explicitly calls out SVG
grouping and transform-origin reliability across browsers. \[Vercel Web
Interface Guidelines\]

# 88. Motion library selection engine

The agent must **not install a motion library by reflex**.

First determine the problem.

## 88.1 Motion technology ladder

Use the least powerful system that solves the requirement:

``` text
CSS transition
→ CSS @keyframes
→ CSS scroll-driven animation
→ Web Animations API
→ View Transition API
→ Motion
→ GSAP
→ specialized renderer/player
→ WebGL / Three.js / Rive / Spline
```

This is a capability ladder, not a status ladder.

A more powerful tool is not automatically a better solution.

## 88.2 CSS first

Use CSS for:

``` text
hover
focus
pressed state
simple reveal
simple fade
simple transform
small loading shimmer
simple responsive visual state
simple repeating background animation
```

Do not ship JavaScript for a transition that CSS already handles
cleanly.

Vercel's current guidance explicitly prefers CSS first, then Web
Animations API, then JavaScript animation libraries when needed.
\[Vercel Web Interface Guidelines\]

## 88.3 CSS scroll-driven animation

For modern browsers where the project supports it and the behavior is
simple, consider CSS scroll-driven animations before adding JavaScript
scroll handlers.

Example concept:

``` css
@keyframes reveal {
  from {
    opacity: 0;
    transform: translateY(1rem);
  }
  to {
    opacity: 1;
    transform: translateY(0);
  }
}

.section {
  animation: reveal linear both;
  animation-timeline: view();
  animation-range: entry 10% cover 30%;
}
```

Use this when native scroll-linked behavior improves simplicity and
browser support is appropriate. MDN documents scroll-driven animations
as a CSS feature that can be driven by a scroll or view timeline without
a JavaScript scroll loop. \[MDN --- CSS scroll-driven animations\]

## 88.4 Web Animations API

Use WAAPI when JavaScript must control playback of otherwise
browser-managed animations:

``` text
play
pause
reverse
cancel
finish
change playbackRate
dynamically generate keyframes
coordinate animation objects
```

Example:

``` js
const animation = node.animate(
  [
    { opacity: 0, transform: 'translateY(16px)' },
    { opacity: 1, transform: 'translateY(0)' }
  ],
  {
    duration: 380,
    easing: 'cubic-bezier(.22,1,.36,1)',
    fill: 'both'
  }
);

// animation.pause();
// animation.reverse();
// animation.cancel();
```

MDN describes WAAPI as direct access to the browser's animation engine,
bridging declarative CSS and dynamic JavaScript control. \[MDN --- Web
Animations API\]

## 88.5 View Transitions

Use the View Transition API when the problem is continuity between UI
states or page views rather than an isolated component animation.

Good cases:

``` text
image gallery item → detail view
list → detail
route → route
same UI object changing location
shared-element-like transitions
```

Example:

``` js
function updateUI() {
  document.querySelector('#panel').classList.toggle('is-open');
}

if (document.startViewTransition) {
  document.startViewTransition(updateUI);
} else {
  updateUI();
}
```

Use named `view-transition-name` only for the elements that benefit from
independent continuity.

MDN documents View Transitions for both same-document and cross-document
transitions and emphasizes their role in preserving context during
changes. \[MDN --- View Transition API\]

## 88.6 Motion

Use Motion when you need a concise JavaScript animation layer with
springs, sequences, scroll-linked behavior, SVG support, or more
flexible animation control than CSS alone comfortably provides.

Official quick-start CDN pattern:

``` html
<script type="module">
  import { animate, scroll } from
    "https://cdn.jsdelivr.net/npm/motion@latest/+esm";
</script>
```

For production deployments, replace `latest` with a reviewed, pinned
version and record that version in the project lockfile/release
evidence.

Motion's current documentation supports npm installation and
script/module CDN usage, and its hybrid engine can animate HTML, SVG,
CSS variables, gradients, SVG paths, and sequences. [Motion](#motion)

## 88.7 GSAP

Use GSAP when the animation system genuinely needs:

``` text
complex timelines
scroll orchestration
pinning
scrubbing
sequencing
SVG path animation
motion paths
advanced easing
large coordinated scenes
complex imperative control
```

Official package installation:

``` bash
npm install gsap
```

Developer-style CDN example:

``` html
<script src="https://cdn.jsdelivr.net/npm/gsap@3.13.0/dist/gsap.min.js"></script>
<script src="https://cdn.jsdelivr.net/npm/gsap@3.13.0/dist/ScrollTrigger.min.js"></script>
```

Then:

``` js
gsap.registerPlugin(ScrollTrigger);
```

Use the current verified version appropriate to the project rather than
blindly copying a historical version. The version above is a concrete
CDN example from the maintained major-version line; verify the current
release before shipping. GSAP's current installation docs list core and
plugins including ScrollTrigger, Flip, Observer, MotionPath, MorphSVG,
ScrollTo, and Text plugins. [GSAP](#gsap-1)

## 88.8 ScrollTrigger

Use ScrollTrigger for scroll-triggered or scrubbed sequences that need
precise start/end relationships, pinning, snapping, callbacks, or
coordinated timelines.

Example:

``` js
gsap.registerPlugin(ScrollTrigger);

gsap.to('.hero-art', {
  y: -120,
  ease: 'none',
  scrollTrigger: {
    trigger: '.hero',
    start: 'top top',
    end: 'bottom top',
    scrub: true
  }
});
```

Do not build a bespoke `scroll` listener that writes styles every frame
when a higher-level scroll animation system or native CSS can express
the same thing. GSAP's ScrollTrigger docs provide optimized scroll
triggering, scrubbing, pinning, snapping, callbacks, responsive
matching, and development markers. \[GSAP ScrollTrigger\]

## 88.9 Lenis

Use Lenis only when the project genuinely benefits from a smooth-scroll
layer and the team accepts the interaction/performance implications.

Concrete developer-style script example from the maintained project
docs:

``` html
<script src="https://unpkg.com/lenis@1.2.3/dist/lenis.min.js"></script>
```

Basic:

``` js
const lenis = new Lenis({ autoRaf: true });
```

Avoid adding smooth scrolling merely because an Awwwards-style reference
uses it. Native scrolling should remain understandable, usable, and
accessible. Lenis positions itself as a lightweight smooth-scroll
library and documents use cases including scroll-linked effects and
WebGL synchronization. [Lenis](#lenis-1)

## 88.10 Lottie / dotLottie

Use Lottie/dotLottie when the designer has a meaningful authored
animation asset, especially when the animation is vector-based and
richer than a few CSS states.

Current official web-component pattern:

``` html
<script
  type="module"
  src="https://cdn.jsdelivr.net/npm/@lottiefiles/dotlottie-wc@latest/dist/dotlottie-wc.js"
></script>

<dotlottie-wc
  src="https://lottie.host/your-animation.lottie"
  autoplay
  loop
  style="width: 320px; height: 320px"
></dotlottie-wc>
```

For production, pin the player version rather than depending on
`latest`, and use a known controlled asset URL/version. LottieFiles
currently documents the `dotlottie-wc` web component as a
framework-agnostic web integration with CDN support and playback
controls. \[LottieFiles\]

Do not use Lottie for a one-property fade that CSS can do cheaper.

## 88.11 Three.js / WebGL

Use WebGL only when spatial depth, 3D rendering, shader effects, or
real-time scene interaction is essential to the experience.

Canonical CDN/import-map pattern:

``` html
<script type="importmap">
{
  "imports": {
    "three": "https://cdn.jsdelivr.net/npm/three@<PINNED_VERSION>/build/three.module.js",
    "three/addons/": "https://cdn.jsdelivr.net/npm/three@<PINNED_VERSION>/examples/jsm/"
  }
}
</script>
```

Three.js officially recommends consistent version/source usage when
importing from a CDN. \[Three.js\]

Do not mix unrelated versions or CDNs for the same WebGL dependency
graph.

## 88.12 Rive / Spline / advanced visual runtimes

Use specialist runtimes when the visual is a true interactive scene or
stateful animation rather than a normal DOM transition.

Examples:

``` text
Rive      → interactive vector/state-machine graphics
Spline    → authored interactive 3D scenes
Three.js  → custom real-time WebGL/WebGPU scene control
Lottie    → authored vector motion asset playback
```

Spline's `<spline-viewer>` is a native custom element designed for
embedding scenes into websites and can connect scene interaction to the
surrounding page. \[Rive/Spline documentation\]

The agent must still validate:

``` text
bundle cost
CPU/GPU cost
mobile behavior
reduced motion
keyboard path
fallback
loading state
failure state
interaction discoverability
```

# 89. Motion library CDN and loading discipline

"Add a CDN" is not a valid implementation plan.

The agent must specify:

``` text
LIBRARY

CDN SOURCE
INTEGRITY / TRUST MODEL

REGISTRATION
INITIALIZATION
CLEANUP

```

## 89.1 Pin dependencies

For production:

``` text
prefer package manager + lockfile
or
pin exact CDN version
```

Avoid silently depending on floating `latest` in production unless the
platform explicitly controls and verifies the asset version elsewhere.

## 89.2 Load only what is needed

Do not load:

``` text
entire animation stack
+ multiple animation libraries
+ multiple icon libraries
+ multiple smooth-scroll libraries
```

when one smaller dependency solves the requirement.

## 89.3 One responsibility per library

Good:

``` text
GSAP → advanced timeline/scroll orchestration
Lucide → interface icons
Lottie → authored illustration animation
Three.js → 3D scene
```

Bad:

``` text
GSAP + Motion + anime.js + Framer Motion
all on the same landing page
```

unless the architecture proves why each is necessary.

## 89.4 Library compatibility audit

Before shipping a new dependency, inspect:

``` text
browser support
SSR compatibility
hydration behavior
ESM/UMD strategy
tree-shaking
bundle size
worker capability
accessibility impact
reduced motion support
licensing
maintenance status
security/advisory history
API stability
```

## 89.5 Cleanup is mandatory

If an animation system creates subscriptions, observers, timelines,
event handlers, or runtime instances, define teardown behavior.

The agent must not leave:

``` text
stale observers
stale ScrollTriggers
orphaned listeners
duplicate timelines
multiple RAF loops
old animation instances
```

after route changes or component unmount.

# 94. Senior developer teaching mode

When the agent is asked to teach rather than simply produce code, it
should teach the **decision process** alongside implementation.

For every advanced technique, explain:

``` text
PROBLEM
WHY THIS TECHNIQUE
WHY NOT A SIMPLER TECHNIQUE
IMPLEMENTATION
ACCESSIBILITY
PERFORMANCE
RESPONSIVENESS
FAILURE MODE
HOW TO VALIDATE
WHEN TO REMOVE IT
```

Example:

``` text
PROBLEM:
A product gallery needs continuity when a thumbnail becomes the featured image.

WHY:
The visual identity of the product remains spatially stable between states.

WHY NOT GSAP:
The browser View Transition API can express this page/state continuity with less
application animation code.

IMPLEMENTATION:
Use view-transition-name on the image and perform the state update through
startViewTransition when available.

FALLBACK:
Perform the normal state update without the transition.

VALIDATION:
Keyboard, reduced motion, slow device, Safari/Chrome/Firefox, route interruption.
```

This turns the skill into a **teacher of engineering judgment**, not
merely a repository of snippets.

# 96. Final agent release contract for asset-rich premium websites

A website is ready to present only when the agent can establish:

``` text
INTENT
✓ The primary user goal is obvious.

SEMANTICS
✓ HTML meaning survives without styling.

IMAGERY
✓ Every major image has a role, source, crop strategy, and loading strategy.

ICONS
✓ UI symbols form a coherent semantic system.

TYPOGRAPHY
✓ Type hierarchy, measure, wrapping, weight, and loading are intentional.

COLOR / GRADIENTS
✓ Color and gradients support hierarchy rather than filling empty space.

MATERIALS
✓ Morphism is selected for a communication purpose, not trend compliance.

MOTION
✓ Motion has a reason, correct trigger, timing, origin, and fallback.

LIBRARIES
✓ Every third-party animation/icon/runtime dependency is justified.

CDN
✓ External dependencies are versioned or intentionally controlled.

RESPONSIVE
✓ Images, icons, typography, materials, and motion adapt at real widths.

ACCESSIBILITY
✓ Keyboard, focus, semantics, contrast, reduced motion, and names work.

PERFORMANCE
✓ Image, font, JS, animation, and third-party costs are understood.

TRUTH
✓ Assets and visual claims do not fabricate real-world evidence.

QA
✓ The page was rendered, inspected, corrected, and rechecked.

POLISH
✓ The final pass removed unnecessary visual residue.
```

## Final principle

> **The agent should not ask "What cool effect can I add?"**
>
> It should ask:
>
> **"What does the user need to understand, feel, choose, or accomplish
> --- and what is the smallest, strongest combination of semantics,
> imagery, icons, typography, color, materials, and motion that
> communicates it?"**

That is the difference between generated decoration and professional
frontend craft.
